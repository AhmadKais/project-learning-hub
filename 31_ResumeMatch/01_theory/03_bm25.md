# Step 3 — BM25, and what TF-IDF gets wrong

TF-IDF is good. BM25 is better, and it is worth understanding exactly why —
this comparison **is** your project.

## Problem 1 — repetition counts too much

In TF-IDF, weight is **linear** in term frequency:

```
"Python" 2 times  ->  weight 2 × idf
"Python" 20 times ->  weight 20 × idf      ... ten times more
```

Is a candidate who wrote "Python" 20 times ten times more expert than one who
wrote it twice? Obviously not. They repeated themselves.

**BM25's answer: saturation.**

```
        tf × (k1 + 1)
    ---------------------
        tf + k1
```

With `k1 = 1.5`:

| tf | factor | gain over previous |
|---|---|---|
| 1 | 1.00 | — |
| 2 | 1.43 | +0.43 |
| 5 | 1.92 | small |
| 20 | 2.33 | tiny |
| ∞ | 2.50 | the ceiling is `k1 + 1` |

The first mention tells you a lot. The twentieth tells you almost nothing.
The curve climbs steeply, then flattens.

❓ **What does `k1` control?**

How fast it flattens. Small `k1` → saturates almost immediately (any mention
counts the same). Large `k1` → behaves more like plain TF-IDF.

## Problem 2 — length

Cosine handles length by geometry. BM25 handles it **explicitly**, with a knob:

```
    tf + k1 × (1 - b + b × |d| / avgdl)
                              ^^^^^^^^^
                    this document's length ÷ the average length
```

- `|d| / avgdl > 1` → longer than average → denominator grows → score drops
- `|d| / avgdl < 1` → shorter than average → score rises

And `b` controls how strongly:

- `b = 0` → the whole bracket becomes 1 → **length ignored completely**
- `b = 1` → full correction
- `b = 0.75` → the standard compromise

💡 **`b = 0` is your experiment.** Run the ranking with `b = 0` and with
`b = 0.75` and compare. If long CVs suddenly climb the rankings at `b = 0`, you
have *proved* that length normalisation matters — with data, not opinion. This
is the single most important chart in your project book.

## The full formula

```
                              tf × (k1 + 1)
score = Σ   idf_bm25(t) × ---------------------------------------
      t∈query               tf + k1 × (1 - b + b × |d|/avgdl)
```

📄 **Write it in this exact shape in your code**

```python
def _term_score(self, tf, doc_length, idf):
    numerator = tf * (self.k1 + 1)
    denominator = tf + self.k1 * (1 - self.b + self.b * doc_length / self.avgdl)
    return idf * numerator / denominator
```

Someone reading your code next to the proposal should recognise it instantly.

## BM25 uses a different IDF

⚠️ This catches people out:

```python
idf_bm25 = math.log((N - df + 0.5) / (df + 0.5) + 1)
```

Not the same formula as TF-IDF's. Using the wrong one is a **silent** accuracy
bug — nothing crashes, the rankings are just quietly worse.

❓ **What is the `+ 1` inside the log for?**

Without it, a term appearing in more than half the documents gets a *negative*
IDF, and would actively **subtract** from the score. A common word making a
candidate worse makes no sense. The `+ 1` keeps it positive.

## Inverted index

For BM25 we do not build a matrix. We build a dictionary:

```python
inverted = {
    "python": [(0, 2), (1, 1)],     # (document row, term frequency)
    "django": [(0, 1)],
    "java":   [(1, 1), (2, 1)],
}
```

To rank a job, walk **only** the terms in the job:

```python
for term in set(job_terms):
    if term not in self.inverted:
        continue
    for doc_row, tf in self.inverted[term]:
        scores[doc_row] += self._term_score(tf, self.doc_len[doc_row], idf[term])
```

A CV sharing no word with the job is **never touched**. It scores 0 without
being looked at. This is how a search engine ranks millions of pages in
milliseconds, and it is worth saying out loud in your defence.

💡 Count how many documents you actually touch versus the collection size. Put
that number in the book — it is direct evidence the index does its job.

## Comparing the two scores fairly

Cosine is already between 0 and 1. BM25's raw score is **unbounded** — it could
be 3.7 or 41.2 depending on the query.

So comparing raw numbers is meaningless. Normalise by the best score in the
current ranking:

```python
top = max(scores)
normalised = [s / top for s in scores] if top > 0 else scores
```

⚠️ State the limitation in your book: this makes scores comparable **within one
ranking**, not between two different jobs. For the research comparison, compare
**rank positions** instead — position is immune to scale entirely.
