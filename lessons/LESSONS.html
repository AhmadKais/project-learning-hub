Lesson 01 — What "learning" means: data, splits and overfitting

For: Laith (Spam) · Ryan (FaceEmotion) · Dani (PhishGuard) · Seif (WineGrader)  ·  Time: 1 × 45 min Before: nothing  ·  After this: every other ML lesson (02 – 05, 11 – 24)

🎯 By the end, the student can

  1. Say in one sentence how machine learning differs from normal programming.
  2. Explain what train, validation and test data are for, and why the test set is used only once.
  3. Recognise overfitting and underfitting on a picture, and say how to detect them with numbers.

1. The picture to start with

Say it: in normal programming you write the rules. In machine learning you give the computer examples with the correct answers, and it finds the rules. The rules it finds are called the model.

Ask the class: "Write me a rule that catches every spam SMS." Collect 3 answers ("contains FREE", "contains a link" …) and break each one with a counter-example ("FREE parking at the meeting tomorrow"). That is why the projects learn instead.

2. Words you must know

Word Meaning In the projects
example (sample, row) one thing we know the answer for one SMS · one URL · one wine · one face picture
feature one number that describes the example num_dots of a URL · alcohol of a wine · one pixel
label the correct answer spam/ham · good/bad · low/medium/high · one of 7 emotions
model the rules the computer learned Naive Bayes · logistic regression · k-NN · EmotionNet
training finding the model from labelled examples fit(X, y)
prediction using the model on a new example predict(x)
hyper-parameter a setting you choose, not learned alpha, C, k, learning rate
generalisation doing well on examples it never saw the only thing that counts

3. The three piles of data

Pile What it is for School analogy
train the model learns from it the textbook and the homework
validation you compare models and choose settings (k, C, threshold) the mock exam
test measured once, at the end, and reported the real exam

🔑 If you look at the test set while choosing anything, it is no longer an exam — it is homework you already saw. The number you report is then a lie (a too-good one). This is called leakage (Lesson 05).

Stratified split: every pile keeps the same percentage of each class. In the SMS data only 13 % is spam; a random split could put almost no spam in the test pile by bad luck.

4. Overfitting — watch it happen

(Projector version: videos/overfitting.mp4. Live version with a slider: python visualize.py --live.)

The blue dots are the training data: a wave plus noise. We fit a polynomial of growing degree.

Degree What you see Name
0 – 2 a flat or bent line that misses the wave underfitting — too simple
3 – 6 follows the wave, ignores the noise good fit
7 – 15 wiggles through every blue dot, wild between them overfitting — memorised the noise

The right panel is the whole lesson: the error on the training data (blue) only goes down — a more complex model can always memorise more. The error on new data (orange) goes down, then up. We choose the model at the bottom of the orange curve, and we can only see that curve with data the model did not train on.

Analogy: a student who memorises the answers of last year's exam gets 100 on it, and fails this year's.

5. Bias and variance — the dartboard

Imagine training the same model on 12 different samples of data — every dart is one trained model.

  • Bias = the model is systematically wrong (centre of the darts is off) → too simple → underfitting.
  • Variance = the model changes a lot with the data (darts scattered) → too complex → overfitting.
You see in your results Diagnosis What to try
train score low, validation score low high bias more features, bigger model, less regularisation
train score high, validation score much lower high variance more data, simpler model, more regularisation, augmentation
both high and close 🎉 stop tuning, write the book

6. Common misconceptions

Student says The truth How to show it
"99 % on training data — my model is great" training score says nothing about new data the blue curve in the animation reaches ~0 at degree 15
"I'll just test on the test set a few times while I tune" every look leaks; the final number becomes optimistic Lesson 05, the leakage demo
"More complex model = better" only until the orange curve turns up the animation
"Accuracy is enough" with 87 % ham, "always ham" scores 87 % Lesson 03

7. Activities

  1. Predict, then watch (5 min). Before showing the GIF ask: "what will degree 15 look like?" Each student draws their guess on paper. Then play it.
  2. Human overfitting (10 min). Give 6 cards with made-up "wine" data (alcohol, colour → good/bad), one of them mislabelled. Students write the rule. Someone always writes a rule that fits the wrong card too — show them it fails on 4 new cards.
  3. Find the pile (5 min). Read sentences aloud; the class shouts train / validation / test: "choose k for k-NN" (validation) · "the number in the book's results chapter" (test) · "count words per class for Naive Bayes" (train) · "choose the spam threshold" (validation).

8. Check yourself

1. Why can't we choose the threshold of the spam filter on the test set?

Because then the test set took part in building the system. The precision we then report from the same data is no longer a measurement on unseen data — it is optimistic, and we cannot know by how much.

2. Train accuracy 0.99, validation 0.71. What is happening, and two things you try?

Overfitting (high variance). Try a simpler model / more regularisation (smaller C, bigger alpha, more dropout), more data, or data augmentation (FaceEmotion).

3. A wine dataset has 19 % "high" wines. Why do we split stratified?

So that every pile has ≈19 % high wines. Otherwise by luck the validation pile might have very few, and every number measured on it (recall of "high") would be noise.

Lesson 02 — Feature scaling: making every feature speak the same language

For: Seif (WineGrader — critical) · Dani (PhishGuard) · Laith (SVM) · Ryan (pixel normalisation)  ·  Time: 45 min Before: Lesson 01  ·  After this: Lessons 12 (logistic regression), 14 (SVM), 15 (k-NN), 19 (images)

🎯 By the end, the student can

  1. Explain with a picture why an unscaled feature with big numbers "wins" every distance.
  2. Compute a z-score and a min-max score by hand, and say which one an outlier breaks.
  3. State the rule: fit the scaler on the training rows only, then use the same numbers for everything else.

1. The problem in one picture

Wine features: alcohol is 8 – 14, density is 0.99 – 1.04, total SO₂ is 9 – 440. A distance just adds the differences up, so a difference of 50 in SO₂ (ordinary) completely drowns a difference of 3 % alcohol (huge).

Left: the 7 "nearest" wines to the blue star, using raw numbers. They are all at SO₂ ≈ 140, and their alcohol is anything from 8.8 to 11.7 — alcohol is ignored. Right: after scaling, the neighbours are close in both features.

Analogy: comparing two people by "height in millimetres + age in years". Height decides everything; a 2-year-old and a 60-year-old of the same height look like twins.

2. Definitions

Name Formula After it Breaks when
z-score (standardisation) z=x−meanstdz = \dfrac{x - \text{mean}}{\text{std}} mean 0, std 1 — "how many typical steps away from average" std = 0 (constant feature → set std to 1)
min-max z=x−minmax−minz = \dfrac{x - \min}{\max - \min} everything in [0, 1] one outlier squeezes everyone else

3. Watch z-score happen

Two moves, nothing else: slide the cloud so its centre is at 0 (subtract the mean), then squeeze/stretch each axis so its spread is 1 (divide by the std). The shape of the cloud — who is close to whom inside each feature — does not change.

4. By hand (do it on the board)

Alcohol of three training wines: 8, 10, 12.

mean = (8 + 10 + 12) / 3 = 10
std  = sqrt( ((8-10)² + (10-10)² + (12-10)²) / 3 ) = sqrt(8/3) = 1.633     (numpy's np.std, ddof = 0)

z(8)  = (8 - 10) / 1.633  = -1.22
z(10) = 0
z(12) = +1.22

min-max:  (8-8)/(12-8) = 0     (10-8)/4 = 0.5     (12-8)/4 = 1

A new wine with alcohol 13 arrives → z = (13 − 10) / 1.633 = 1.84 using the training mean and std. Min-max gives (13 − 8) / 4 = 1.25 — outside [0, 1], and that is fine.

5. Outliers: why WineGrader prefers z-score

One white wine has 440 mg/l SO₂. With min-max that wine is 1.0 and the other 4,897 wines are pressed into the bottom part of the range, so their differences become tiny. z-score is hurt much less. (Both are in Seif's hyper-parameter search; the tuning table decides — test_one_outlier_squeezes_minmax_but_not_zscore.)

6. Scaling also makes learning faster

For models trained with gradient descent (logistic regression, SVM, neural networks): unscaled features make the error surface a long narrow valley. The step that is safe for the steep direction is far too small for the flat one, so the optimiser zig-zags and crawls. Scaled features make the valley round — it walks straight down. That is what LinearSVC means when it warns "failed to converge" (Laith, StandardScaler before the SVM).

7. THE rule (the one examiners ask about)

# RIGHT                                         # WRONG - leaks the test rows into the model
scaler = StandardScaler().fit(X_train)          Z = StandardScaler().fit_transform(X_all)
Xtr = scaler.transform(X_train)                 Xtr, Xte = Z[train], Z[test]
Xte = scaler.transform(X_test)   # TRAIN numbers

The mean and std are learned → they are part of the model → they come from the training rows only → they are saved with the model and used again for every new example in the app.

8. Misconceptions

Student says Truth
"Scaling changes my data, so it changes the answer" It changes distances between features, which is exactly the point. Inside one feature the order of the wines is unchanged.
"Naive Bayes / random forest also need scaling" No. NB counts words; a tree asks "is x > 3?" — scaling moves the threshold, not the split. Only distance- and gradient-based models need it.
"Fit the scaler on everything, it's just a mean" Leakage. Small, but real — and there are tests that catch it.
"At prediction time I'll scale the one new example by itself" The std of one value is 0. Use the saved training numbers.

9. Activities

  1. Human k-NN (10 min). Write 5 "people" on the board as (height cm, age years). Ask who is closest to a new person. Then convert to z-scores together and ask again — the answer changes.
  2. Slider (5 min). python visualize.py --live — the slider multiplies SO₂ by a weight. At 0 SO₂ is ignored; at 3 it dominates again. This is also the idea behind Seif's feature weights (Lesson 17).

10. Check yourself

1. Training alcohol: mean 10.5, std 1.2. A new wine has 12.3. Its z-score?

(12.3 − 10.5) / 1.2 = 1.5 — one and a half typical steps above average.

2. Why does a random forest not care about scaling?

Every split is a question "feature ≤ threshold?". Scaling is a monotonic change of the axis, so the same examples go left and right — only the threshold number changes.

3. A feature is the same for every training wine. What does the z-score do, and what should it do?

std = 0 → division by zero. Set std to 1: the column becomes all zeros and adds nothing to any distance — right, because it carries no information.

Lesson 03 — Measuring a classifier: confusion matrix, precision, recall, F1

For: Laith · Dani · Seif · Ryan (and Kosai for precision in Lesson 10)  ·  Time: 45 – 60 min Before: Lesson 01  ·  After this: Lesson 04 (threshold, ROC)

🎯 By the end, the student can

  1. Fill a confusion matrix from predictions, and name the four cells with their meaning in their own project.
  2. Compute precision, recall, F1 and accuracy by hand, and explain why accuracy lies on imbalanced data.
  3. Explain macro-F1 for more than two classes (Wine: 3 grades, Face: 7 emotions).

1. Start with the picture: the fishing net

Orange squares are spam, blue dots are real messages. The yellow circle is "what the filter calls spam".

  • Precision = of what is inside the net, how much is spam? (Did I catch only fish, or also boots?)
  • Recall = of all the spam in the sea, how much is inside the net?

A bigger net → higher recall, lower precision. You cannot have both for free. Ask the class before showing the third panel: "What if the net is the whole sea?" (recall 1.0, precision = the share of spam.)

2. The confusion matrix — real numbers from the SMS data

A simple model, 1,673 validation messages, threshold 0.5:

Cell Name In Spam In PhishGuard In WineGrader
TP true positive spam caught phishing blocked — (per class, see §5)
FP false positive real mail hidden 😱 legitimate site blocked
FN false negative spam in the inbox phishing let through 😱
TN true negative real mail delivered legitimate site allowed

😱 marks the expensive mistake. It is a different cell in the two projects — that is why Laith and Dani choose their thresholds with opposite rules (Lesson 04).

3. The formulas, and the same numbers by hand

precision=TPTP+FPrecall=TPTP+FNF1=2PRP+Raccuracy=TP+TNall\text{precision}=\frac{TP}{TP+FP}\qquad \text{recall}=\frac{TP}{TP+FN}\qquad F_1=\frac{2PR}{P+R}\qquad \text{accuracy}=\frac{TP+TN}{\text{all}}

TP = 187   FP = 5   FN = 37   TN = 1444          (all = 1673)

precision = 187 / 192  = 0.974     "when it says spam, it is right 97% of the time"
recall    = 187 / 224  = 0.835     "it catches 83% of the spam"
F1        = 2·0.974·0.835 / (0.974 + 0.835) = 0.899
accuracy  = 1631 / 1673 = 0.975

Memory trick: Precision looks at the Predicted column. Recall looks at the Real row.

Why F1 is a harmonic mean: if P = 1.0 and R = 0.0, the ordinary average is 0.5 — a useless model looks "half good". The harmonic mean gives 0: F1 is only high when both are high.

4. Accuracy lies on imbalanced data

87 % of the SMS are ham. A "model" that always answers ham has 87 % accuracy and catches nothing. Every ML project here is imbalanced (spam 13 %, high-quality wine 19 %, "disgust" in FER-2013 ≈ 1.5 %), so accuracy is never the main number in their books.

5. Watch everything move with the threshold

Left: the model's scores for real ham (blue) and real spam (orange). Everything right of the black line is called spam. Middle: the matrix. Right: precision, recall and F1 for every threshold. Pause the video at three places and let the students read the four numbers aloud. Questions to ask while it plays:

  • "Why does FP explode when the line goes left?" (the big blue pile is on the left)
  • "Where is F1 highest? Is that where Laith should put his threshold?" (No — Lesson 04.)

6. More than two classes: macro-F1

For each class, treat it as "positive" and all others as "negative", and compute P, R, F1. Then:

  • macro-F1 = the plain average of the per-class F1s → every class counts the same, even the small "high".
  • accuracy is dominated by the big classes.

Reading the matrix: the row is the truth, the column the prediction, the diagonal is correct. Most errors in wine are between neighbouring grades (low↔︎medium, medium↔︎high) — the tasters themselves disagree there. (This quick model is untuned; Seif's tuned k-NN reaches ≈ 0.58.)

7. Misconceptions

Student says Truth
"Precision and recall are the same thing basically" Same numerator, different denominator: predicted column vs real row.
"My accuracy is 97 %, done" Compare with the "always majority" baseline first.
"High recall is always good" Calling everything positive gives recall 1.0. Always report both.
"F1 is the best threshold" F1 treats FP and FN as equally bad — they are not in any of these projects.

Lesson 04 — The threshold is a decision: ROC, AUC and choosing where to cut

For: Laith (precision floor) · Dani (ROC, recall target) · Ryan, Seif (reading curves)  ·  Time: 45 min Before: Lesson 03  ·  After this: the threshold stage of Spam (stage 6) and PhishGuard (stage 4)

🎯 By the end, the student can

  1. Explain that a classifier outputs a score, and the threshold turns it into a decision.
  2. Read and draw a ROC curve; say what AUC = 0.5 and AUC = 1 mean; explain AUC as "the chance a random positive outranks a random negative".
  3. Apply their project's rule for choosing the threshold, on the validation set only, and defend it.

1. Every threshold is one point of the ROC curve

Real PhishGuard URLs, a simple model. Left: the scores of legitimate URLs (blue) and phishing URLs (orange). The black line is the threshold; everything to its right is blocked. Right: for that threshold we plot

  • x = false-alarm rate (FPR) = FP / all legitimate — "how many good sites did I block?"
  • y = recall (TPR) = TP / all phishing — "how many attacks did I catch?"

At threshold 1.0 nothing is blocked → (0, 0). At 0.0 everything is blocked → (1, 1). In between the line slides, and the dot draws the curve. The area under it is the AUC.

2. Shapes of ROC curves

AUC Meaning
1.0 the two piles do not overlap at all — some threshold is perfect
0.9 – 0.99 good: little overlap (PhishGuard target ≥ 0.97)
0.5 the diagonal — the scores carry no information, a coin flip
< 0.5 worse than a coin… flip the model's answers and it becomes good (a bug, usually swapped labels)

3. What AUC means, in one sentence

Take one random phishing URL and one random legitimate URL. AUC is the probability that the phishing one gets the higher score. Green lines are pairs in the right order, red ones are wrong. That is why AUC does not depend on any threshold — it is about the ranking, which makes it the fairest single number to compare two models (Dani: logistic regression vs random forest).

4. Choosing the threshold — two projects, two opposite rules

Spam (Laith) PhishGuard (Dani)
expensive mistake FP — real mail hidden FN — phishing let through
constraint precision ≥ 0.98 recall ≥ 0.95
then the threshold with the highest recall the highest threshold (fewest false alarms)
nothing meets the constraint raise an error (never fall back to 0.5) fall back to config.DEFAULT_THRESHOLD
function choose_threshold in ml/threshold.py ModelEvaluator.choose_threshold

Both are scanned on the validation split. The test split only measures the chosen threshold, once.

Algorithm (Laith's version) — write it on the board:

best = none
for t from START to STOP in steps of STEP:
    P, R = precision and recall when "spam" means p >= t
    if P >= 0.98 and (best is none or R > best.R):
        best = (t, P, R)
if best is none: raise ValueError("no threshold reaches precision 0.98; best was ...")
return best

5. Why not just 0.5 or "best F1"?

Give each mistake a price. When a missed phish costs the same as a false alarm, the cheapest threshold is in the middle. When it costs 20×, the cheapest threshold moves left — block more, accept more false alarms. 0.5 and max-F1 both secretly assume the two mistakes cost the same.

6. Misconceptions

Student says Truth
"The model decides spam or not" The model gives a score; you decide where to cut.
"AUC 0.97 means 97 % accuracy" AUC is about ranking, accuracy about one threshold. Different things.
"I'll tune the threshold on the test set — it's just one number" It is a decision → leakage. Validation only.
"Lower threshold = better model" It is the same model; you are only moving along its curve.

Lesson 05 — Honest evaluation: cross-validation, nested CV and leakage

For: Seif (nested CV — the heart of his evaluation) · Laith (SVM grid search) · Dani (grid search) · everyone (leakage) Time: 60 min  ·  Before: Lessons 01, 03  ·  After this: the tuning stages of the ML projects

🎯 By the end, the student can

  1. Explain k-fold cross-validation with the picture, and why it is better than one validation split.
  2. Explain why folds must be stratified, and why duplicates must be removed before splitting.
  3. Draw nested cross-validation and explain what each loop is for.
  4. Name the four common leaks and the guard against each.

1. One validation split is one roll of the dice

With 300 validation wines, which wines happened to land there can move the score by a few points. Choosing k = 15 over k = 17 on such noise means choosing by luck. Cross-validation uses every row for testing once, and averages.

2. k-fold cross-validation — watch it

  1. Cut the (shuffled) data into k folds (here 5).
  2. Round i: fold i is the test set, the other 4 folds are training. Train, score.
  3. Report the mean ± standard deviation of the 5 scores.

Real wine numbers (5,320 unique wines, k-NN): 0.606, 0.573, 0.574, 0.564, 0.593 → 0.582 ± 0.015. The ± is as important as the mean: if two settings differ by less than it, they are a tie.

3. Stratified folds

On a small sample, random folds can have 5 % "high" wines in one fold and 30 % in another — every fold measures a different problem. Stratified folds deal each class out separately, like dealing cards suit by suit, so each fold keeps the overall share. (Seif writes this by hand: stratified_kfold in winegrader/ml/folds.py.)

4. Leakage — the test set must know NOTHING

Leakage = information from the test rows gets into the model or into a decision. The score becomes too good, and nothing crashes. Two real demonstrations:

4a. Pure noise, 89 % accuracy

100 rows, 5,000 random features, labels are coin flips — nothing can be learned. Picking the 20 features "most related to the label" using all rows, then cross-validating, scores 89 %. Doing the same selection inside each training fold scores 55 % — a coin flip, the truth. The leak is invisible in the code unless you know to look for it.

4b. The duplicate trap (WineGrader, real data)

1,177 wines are exact copies of other wines. With them, a 1-NN finds the test wine's own twin at distance 0 and "predicts" its label: macro-F1 0.676. Without them: 0.539. Remove duplicates before splitting — after splitting is too late, because each copy looks unique in its own part.

The four leaks and their guards

Leak Guard Projects
a row (or its copy) in both train and test remove duplicates before splitting; assert_no_leakage Wine, Spam
scaler / vocabulary / IDF / feature selection fitted on all rows fit inside the training part (a Pipeline) all ML
hyper-parameters or threshold chosen on test validation set, or nested CV all ML
looking at the final test number and trying again run the final evaluation once all — "your discipline"

5. Nested cross-validation

If we use CV both to choose k, p, alpha and to report the score, the reported score is the best of many tries — optimistic. Nested CV separates the two jobs:

  • inner loop (3 folds, only on the outer-training rows) → chooses the setting;
  • outer loop (5 folds) → measures the whole procedure "tune, then train", each outer test fold scored once.
for train, test in outer_splits:                       # 5 times
    inner  = stratified_kfold(y[train], 3)
    tuned  = grid_search(X[train], y[train], inner)    # never sees X[test]
    w      = learn_weights(X[train], y[train], tuned.best, inner).weights
    result = evaluate_split(model_with(tuned.best, w), X, y, train, test, ...)

How Seif proves it: test_nested_never_sees_outer_test scrambles the outer test labels and runs again. The chosen parameters must be identical — the procedure cannot react to labels it never looked at.

6. Misconceptions

Student says Truth
"CV trains one model 5 times" It trains 5 different models; CV measures the procedure, then you train one final model on all training data.
"Higher CV score with duplicates = better" Better at looking up answers, not at grading wine.
"Nested CV gives me the best parameters" It gives an honest score. Different outer folds may choose different parameters; that's expected and goes in the book.
"A small leak doesn't matter" You cannot know how big it is — that is why it matters.

Lesson 07 — TF-IDF: turning text into numbers that mean something

For: Kosai (ResumeMatch stages 3–4) · Laith (SpamClassifier stage 3)  ·  Time: 45 – 60 min Before: Lesson 06  ·  After this: Lesson 08 (cosine), 09 (BM25), 11 (Naive Bayes)

🎯 By the end, the student can

  1. Build a bag-of-words matrix by hand.
  2. Compute df, idf and tf-idf for a small example — with their project's exact formula — and explain each +1.
  3. Explain L2 normalisation and why a long document must not win just by being long.

1. Bag of words

Every document becomes a row, every term a column, every cell a count. Word order is lost (a "bag"). A real CV row has thousands of columns and almost all are 0 — a sparse vector — so we store it as a dictionary {"python": 2, "sql": 1} instead of a long list of zeros.

Problem: raw counts reward words that are everywhere ("experience", "team") and long documents.

2. TF-IDF, built step by step

Step Formula (ResumeMatch) On the example
tf count of the term in this document python in CV 1 = 2
df number of documents that contain the term python = 2, sql = 3, docker = 1
idf ln1+N1+df+1\ln\frac{1+N}{1+df}+1 python = ln(4/3)+1 = 1.2877 · sql = ln(4/4)+1 = 1.0 · docker = ln(4/2)+1 = 1.6931
tf-idf tf × idf CV 1: python 2 × 1.2877 = 2.58, sql 1.00, docker 1.69
L2 divide the row by ∑v2\sqrt{\sum v^2} CV 1: √(2.58² + 1² + 1.69²) = 3.24 → 0.79, 0.31, 0.52

Read it aloud: "sql is in every CV, so it barely matters. docker is only in CV 1, so it's what makes CV 1 special."

3. The IDF curve — and the two +1s

Piece Why
the log without it, a term in 5 docs would be 40× a term in 190 docs; the log makes importance grow slowly
1 + inside no division by zero; a little smoothing
+ 1 outside a term in every document gets weight 1, not 0 — weakened, not deleted

tf idf
ResumeMatch (Kosai) raw count ln((1 + N) / (1 + df)) + 1 → check values 1.2877 / 1.6931 / 1.0000

4. On the project's real CVs

Left: what the CV repeats. Right: what makes it different. Skills like figma and webpack rise — and so does the candidate's name, because it is rare. That is not a feature, it is a bias: the reason Kosai's pipeline scrubs names, e-mails and phone numbers before counting.

5. L2 normalisation — why

Two CVs: one says "python" once in 50 words, the other pastes the same paragraph 4 times. Without normalisation the second has 4× bigger numbers everywhere and wins every comparison. After dividing by the length, both rows have length 1 and only the proportions (the direction, Lesson 08) remain. Laith: test_long_and_short_messages_are_comparable.

6. The bug everyone makes once

df = Counter()
for doc in docs:
    df.update(set(doc))      # set()! each term counts ONCE per document

Without set() you count occurrences, not documents. A word shouted 500 times in one e-mail gets df = 500 and looks "common". Tests: test_document_frequency_counts_documents_not_occurrences (Kosai), the vocabulary test (Laith).

Student says Truth

"Compute IDF on all documents including test" Leakage (Lesson 05). Fit on training; the same IDF transforms new documents.
"A term in every document gets IDF 0" Not with these formulas — it gets 1 (the +1 outside).
"TF-IDF understands meaning" It counts. "java" (coffee) = "java" (language). Synonyms do not match.

Lesson 08 — Documents as arrows: dot product and cosine similarity

For: Kosai (ResumeMatch stage 4) · useful for Laith and Seif (vectors, distances)  ·  Time: 45 min Before: Lesson 07  ·  After this: Lesson 09 (BM25), Lesson 10 (P@k, MRR)

🎯 By the end, the student can

  1. Draw two documents as arrows and explain similarity as the angle between them.
  2. Compute a dot product, a vector length and a cosine by hand.
  3. Explain why cosine (not distance) is used for text, and why after L2 normalisation cosine = dot product.

1. A document is an arrow

With only two terms (python, sql) every document is a point / an arrow in 2-D. With 5,000 terms it is an arrow in 5,000-D — we cannot draw it, but the maths is identical.

  • CV A = (2, 1) and CV B = (4, 2): B is A "said twice". Same direction, same cosine 0.949.
  • CV C = (0, 3) only talks about sql: a bigger angle, cosine 0.707.

2. The formulas

a⋅b=∑iaibi∥a∥=∑iai2cos(a,b)=a⋅b∥a∥∥b∥a\cdot b=\sum_i a_i b_i\qquad \|a\|=\sqrt{\sum_i a_i^2}\qquad \cos(a,b)=\frac{a\cdot b}{\|a\|\,\|b\|}

By hand, job J = (1, 1) and CV A = (2, 1):

dot    = 1·2 + 1·1           = 3
|J|    = √(1 + 1)            = 1.414
|A|    = √(4 + 1)            = 2.236
cos    = 3 / (1.414 · 2.236) = 0.949        angle = arccos(0.949) ≈ 18°

3. Watch the angle

cosine angle meaning
1 0° same proportions of words
0 90° no word in common
< 0 > 90° impossible with word counts — all values are ≥ 0

So for text, cosine is always between 0 and 1 — a nice score to show a recruiter.

4. Why not just measure the distance?

Euclidean distance punishes the CV that is just longer: "same CV × 5" is the farthest. Cosine looks only at the direction, so length stops mattering. This is the same reason as L2 normalisation (Lesson 07).

The trick that makes Kosai's code simple: if every row is already divided by its length, then ∥a∥=∥b∥=1\|a\|=\|b\|=1 and

cos(a,b)=a⋅b\cos(a,b)=a\cdot b

Ranking 200 CVs = one matrix × vector product.

5. On the real data — and a surprise

Job J1 against all 200 CVs. 8 of the top 10 are CVs a human marked relevant (P@10 = 0.8, Lesson 10). But the top two are wrong: CVs that pasted the job advert into their text. Cosine measures word overlap, not skill. This is why Kosai's system has a reliability check (RankExplainer.warning_for): a CV that matches the advert's sentences but not its skills gets a warning.

6. Algorithm (ResumeMatch's rank)

Lesson 09 — BM25 and the inverted index: how search engines rank

For: Kosai (ResumeMatch stage 5 — the comparison that is his project)  ·  Time: 60 min Before: Lessons 07, 08  ·  After this: Lesson 10 (measuring the ranking)

🎯 By the end, the student can

  1. Name the two things TF-IDF gets wrong (repetition, length) and show how BM25 fixes each, with the picture.
  2. Explain what k1 and b do, and predict what b = 0 will do to the ranking.
  3. Compute one BM25 term score by hand, with the BM25 IDF (not the TF-IDF one).
  4. Explain the inverted index and why it makes search fast.

1. The formula, piece by piece

score(d,q)=∑t∈qidfbm25(t)⋅tf(k1+1)tf+k1(1−b+b|d|avgdl)\text{score}(d,q)=\sum_{t\in q}\ \text{idf}_{bm25}(t)\cdot\frac{tf\,(k_1+1)}{tf+k_1\left(1-b+b\,\frac{|d|}{avgdl}\right)}

Do not start with the whole formula. Build it from two problems.

2. Problem 1 — repetition counts too much → saturation

In TF-IDF "python" ×20 counts 10× more than "python" ×2. BM25's factor tf(k1+1)tf+k1\frac{tf(k_1+1)}{tf+k_1} climbs fast and then flattens at the ceiling k1+1k_1+1. With the project's k1=1.5k_1 = 1.5:

tf 1 2 5 20 ∞
factor 1.00 1.43 1.92 2.33 2.50

The animation sweeps k1k_1: small k1k_1 → "mentioned at all" is all that matters; large k1k_1 → almost linear like TF-IDF. (The project's data has "keyword stuffers" who repeat one skill 15 times — saturation stops them.)

3. Problem 2 — length → the b knob

|d|/avgdl|d|/avgdl = "how long is this CV compared to an average CV". A long CV mentions many things just by being long, so the same tf is worth less. b says how strongly to correct: 0 = ignore length, 1 = full, 0.75 = standard.

The experiment on the project's data

With b = 0 the top-10 CVs are on average 136 terms long (average CV: 100). With b = 0.75 they are 79. On this data P@10 barely changes (0.86–0.88) — the human labels are by role, and long CVs of the right role are still relevant. That is a result too. Kosai reports both charts and explains them; he does not hide the flat one.

4. BM25 has its own IDF

idfbm25(t)=ln(N−df+0.5df+0.5+1)\text{idf}_{bm25}(t)=\ln\left(\frac{N-df+0.5}{df+0.5}+1\right)

Without the +1 inside the log, a word in more than half of the CVs gets a negative IDF and lowers the score of everyone who mentions it. Using the TF-IDF formula here instead is a silent bug — nothing crashes, the ranking is just worse.

5. One term by hand

N = 200, df(python) = 60, avgdl = 100. CV with tf = 2, |d| = 150. k1=1.5k_1 = 1.5, b=0.75b = 0.75.

idf   = ln((200 − 60 + 0.5) / (60 + 0.5) + 1) = ln(2.322 + 1) = ln(3.322) = 1.2006
norm  = 1 − 0.75 + 0.75 × 150/100           = 0.25 + 1.125  = 1.375
part  = 2 × 2.5 / (2 + 1.5 × 1.375)         = 5 / 4.0625    = 1.2308
score = 1.2006 × 1.2308                                        = 1.4777

Same CV but average length (|d| = 100): norm = 1, part = 5 / 3.5 = 1.4286, score = 1.7151 — more, because it is shorter.

6. The inverted index

Instead of a matrix with a row per CV, keep for every term the list of CVs that contain it (with tf) — like the index at the back of a book. To rank a job, walk only the lists of the job's terms. A CV that shares no word with the job is never touched: its score is 0 without looking at it.

for term in set(job_terms):
    if term not in self.inverted:
        continue
    for doc_row, tf in self.inverted[term]:
        scores[doc_row] += self._term_score(tf, self.doc_len[doc_row], idf[term])

This is how Google ranks billions of pages in milliseconds. Put "documents touched / total" in the book — direct evidence that the index works.

7. Comparing BM25 with cosine fairly

Cosine is in [0, 1]; BM25 is unbounded (3.7 or 41.2 depending on the job). Normalise by the top score of the ranking (Ranker._normalise) — this makes scores comparable within one ranking only. To compare the methods, compare rank positions and P@k / MRR (Lesson 10), not raw numbers.

"The index changes the scores" It changes only which documents are looked at. Same scores as checking every CV.

Lesson 10 — Is the ranking good? Precision@k and MRR

For: Kosai (ResumeMatch stage 6)  ·  Time: 30 – 45 min Before: Lessons 03, 08, 09  ·  After this: the experiments chapter of the book

🎯 By the end, the student can

  1. Explain why a ranking needs different metrics from a classifier.
  2. Compute P@k and reciprocal rank by hand, and MRR over several jobs.
  3. Read a ranking that is good by one metric and bad by the other, and say what it means.

1. Ranking is not classification

A recruiter reads the top ten and stops. Position 47 is worth nothing. So the metrics only look at the head of the list: how many of the first k are right (P@k) and how high is the first right one (RR).

2. Precision@k — walk down the list

P@k=#relevant among the first kkP@k=\frac{\#\text{relevant among the first }k}{k}

⚠️ Divide by k, even if the list is shorter than k (missing places count as misses) — test_precision_denominator_is_k_not_list_length.

3. Reciprocal rank and MRR

RR=1position of the first relevant(0 if none)MRR=average of RR over all jobsRR=\frac{1}{\text{position of the first relevant}}\qquad(0\text{ if none})\qquad\qquad MRR=\text{average of RR over all jobs}

first relevant at 1 2 3 10 never
RR 1.0 0.5 0.33 0.1 0

The worked example from Kosai's tests (do it on the board): ranking [C3, C7, C1, C9], relevant {C1, C7} → P@2 = 1/2 = 0.50, P@4 = 2/4 = 0.50, RR = 1/2 = 0.50.

4. Why report both

  • Ranking A: four good candidates in the top 5, but not the first → high P@5, RR 0.5.
  • Ranking B: the best one first, then nothing → P@5 0.2, RR 1.0.

P@k ignores order inside the top k. MRR ignores everything after the first hit. Neither alone is enough.

5. On the project's data

Simple versions of both methods on the 200 CVs: P@5 = 0.80 for both, P@10 = 0.90 (TF-IDF) vs 0.88 (BM25), MRR 0.57 for both. Why is MRR so low when P@10 is so high? Because an advert copier (Lesson 08) takes position 1 in four of the five jobs — a precise, explainable finding for the book, and the reason for the reliability check.

6. The golden rule of labelling

The "relevant" lists must be made before looking at the system's rankings, by a human, from the CV text. Labelling after seeing the ranking makes the system's mistakes look correct.

7. Misconceptions

Student says Truth
"P@10 = 0.9 means 90 % accuracy" It means 9 of the first 10 are relevant — nothing about the other 190.
"Divide by the number of results returned" Divide by k.
"MRR of 0.57 means the first hit is at position 0.57" MRR is an average of 1/position: 0.57 is "between 1st and 2nd on average".

Lesson 11 — Naive Bayes from scratch: counting your way to a spam filter

For: Laith (SpamClassifier stage 4 — the heart of the project)  ·  Time: 2 × 45 min Before: Lessons 03, 06, 07  ·  After this: Lesson 04 (choosing the threshold), Lesson 14 (the SVM it is compared with)

🎯 By the end, the student can

  1. Explain Bayes' theorem with the area picture, and compute P(spam | "free") from counts.
  2. Say what is "naive" about Naive Bayes, and why it works anyway.
  3. Train Multinomial NB by hand (priors, counts, Laplace smoothing) and classify a message in log space.
  4. Explain the two classic bugs (zero probabilities, underflow) and how the code prevents each.
  5. Read a word's log-odds as the explanation of a verdict.

1. Bayes' theorem as a picture

Real counts from the 5,574 SMS:

  • 13.4 % of messages are spam → the prior P(spam) = 0.134
  • "free" appears in 23.3 % of spam and 1.2 % of ham → the likelihoods
  • among messages with "free": 174 spam, 59 ham → the posterior P(spam | free) = 174 / 233 = 0.75

P(spam∣w)=P(w∣spam)P(spam)P(w)P(\text{spam}\mid w)=\frac{P(w\mid\text{spam})\,P(\text{spam})}{P(w)}

Say it in words: posterior ∝ likelihood × prior. We knew 13 % before; after seeing "free" we believe 75 %.

Analogy — the doctor's test: a test that catches 99 % of a rare disease still gives mostly false alarms if only 1 in 1,000 people has it. The prior matters. (Ask the class to guess first; almost everyone says 99 %.)

2. The naive assumption

A message has many words. NB assumes the words are independent given the class:

P(w1,…,wn∣c)≈P(w1∣c)⋅P(w2∣c)⋯P(wn∣c)P(w_1,\dots,w_n\mid c)\approx P(w_1\mid c)\cdot P(w_2\mid c)\cdots P(w_n\mid c)

It is false ("click" and "here" come together), but for deciding between two classes it works surprisingly well — the errors push both classes in similar ways, and the ranking of the two scores is usually right.

3. Training is just counting

prior[c]   = (messages of class c) / (all messages)
count[c][w]= how many times w appears in all messages of class c
total[c]   = sum of count[c][·]
P(w | c)   = (count[c][w] + α) / (total[c] + α·|V|)          ← Laplace smoothing, α = 1

One pass over the data, no iterations — so "retrain" can be a button in the UI.

Worked example (from Laith's guide — do it on the board)

spam:  [free, money, now]          [free, prize, winner]
ham:   [meeting, tomorrow, office] [project, meeting, notes]
|V| = 10 words,  spam total = 6,  ham total = 6,  priors 0.5 / 0.5

P(free | spam) = (2 + 1) / (6 + 10) = 3/16 = 0.1875
P(free | ham)  = (0 + 1) / (6 + 10) = 1/16 = 0.0625
log_odds(free) = ln(0.1875) − ln(0.0625) = ln 3 ≈ 1.10        → pushes to spam

4. Bug 1 — zeros → Laplace smoothing

Without smoothing, "free" never appears in ham → P(free | ham) = 0 → any message containing "free" has ham probability exactly 0, no matter what else it says. Adding α to every count gives unseen words a small probability instead of none. The α·|V| in the denominator keeps the probabilities summing to 1.

5. Bug 2 — underflow → work in logs

300 words × probability 0.001 = 10⁻⁹⁰⁰ — a float holds nothing below ~10⁻³⁰⁸, so it becomes exactly 0.0 for both classes. Fix: log(a⋅b)=loga+logb\log(a\cdot b)=\log a+\log b — store log-probabilities and add.

score(c)=logP(c)+∑w∈msglogP(w∣c)\text{score}(c)=\log P(c)+\sum_{w\in\text{msg}}\log P(w\mid c)

Getting a probability back without leaving log space:

P(spam)=11+escore(ham)−score(spam)P(\text{spam})=\frac{1}{1+e^{\,\text{score(ham)}-\text{score(spam)}}}

(and clamp the difference at ±700 — exp(710) overflows.) Never exp() each score separately: 0.0 / 0.0.

6. Watch a message being classified

"URGENT! You have won a free prize. Call now to claim your cash award" → tokens urgent free prize call claim cash award. Each word adds its log-likelihood to both scores (bars grow left); the gap between them is the evidence. Bottom: every word's log-odds = its vote.

7. The explanation comes for free

log_odds(w)=logP(w∣spam)−logP(w∣ham)\text{log\_odds}(w)=\log P(w\mid\text{spam})-\log P(w\mid\text{ham})

These numbers are the model — not an approximation of it. "Flagged because: claim (+5.6), prize (+5.4), URLTOKEN (+4.5)". This is why NB is Laith's primary model even if the SVM scores slightly higher: the project requires an exact reason for every verdict.

8. Proving it is right

test_matches_sklearn trains scikit-learn's MultinomialNB(alpha=1.0) on the same data and demands agreement to 1e-9.

Symptom Likely cause
way off everywhere smoothing in the numerator but not the denominator
right order, wrong values forgot `+ α·
right for short, wrong for long left log space too early
wrong only with unseen words smoothing unknown tokens at predict time instead of skipping them

Lesson 12 — Logistic regression and gradient descent: a weighted vote with a squash

For: Dani (PhishGuard — first model, explanations) · the gradient-descent part is also for Ryan (Lesson 21) Time: 2 × 45 min  ·  Before: Lessons 01, 02, 03  ·  After this: Lesson 13 (trees), Lesson 21 (backprop)

1. The model in one line

p=σ(w1x1+w2x2+…+wnxn+b)σ(z)=11+e−zp=\sigma(w_1x_1+w_2x_2+\dots+w_nx_n+b)\qquad\sigma(z)=\frac{1}{1+e^{-z}}

Every feature gets a weight. The model adds weight × value (a vote), adds a bias, and squashes the sum into a probability.

Each bar is weight × value. PhishGuard's Explainer.contributions shows exactly these (on scaled features: "url_length is 2.1 standard deviations above average"). The model is linear: it cannot learn "dots matter only without HTTPS" — that's what the random forest is for (Lesson 13).

truth p loss
phishing 0.76 −ln 0.76 = 0.27

4. Gradient descent — walking downhill

Imagine standing on a hill in fog. You feel the slope under your feet and step downhill. Repeat.

w←w−lr⋅∂loss∂ww\leftarrow w-\text{lr}\cdot\frac{\partial\,\text{loss}}{\partial w}

For sigmoid + log-loss the slope is beautifully simple — "error times input":

∂loss∂wi=(p−y)xi∂loss∂b=p−y\frac{\partial\,\text{loss}}{\partial w_i}=(p-y)\,x_i\qquad\frac{\partial\,\text{loss}}{\partial b}=p-y

  • URL A' (truth 1, p 0.76): error −0.24 → the weights of the features it has go up.
  • URL B (truth 0, p 0.08): error +0.08 → its features' weights go down a little.

Watch it learn (500 real PhishGuard URLs, two features)

Left: the black line is p = 0.5; colour = the model's probability. It starts with bad weights and turns step by step; right: the loss falls. Two features cannot separate the classes well (loss stays at 0.6) — the real model uses all 20.

for epoch in range(2000):
    p = sigmoid(X @ w + b)
    grad_w = X.T @ (p - y) / len(y)     # average of "error × input"
    grad_b = (p - y).mean()
    w -= lr * grad_w
    b -= lr * grad_b

(Dani's exercises ex05–ex08 build exactly this; ModelTrainer.build_logistic then uses scikit-learn, which does the same with a smarter optimiser.)

5. Regularisation — the C parameter

Without a brake the model can grow huge weights to fit noise. L2 regularisation adds ∑w2\sum w^2 to the loss. scikit-learn's C is the inverse strength: small C = strong brake = all weights pulled toward 0 = simpler model. Dani tries C ∈ {0.01, 0.1, 1, 10} with cross-validation (Lesson 05).

6. Misconceptions

Student says Truth
"Logistic regression predicts a number, so it isn't a classifier" It predicts a probability; the threshold makes it a class. The name is historical.
"A big weight = an important feature" Only if features are on the same scale — that's why weights are compared on scaled features.
"A bigger learning rate learns faster" Too big jumps over the minimum and diverges (third panel).
"Gradient descent finds the perfect model" It finds the best linear model for the loss. If the truth isn't linear, it can't.

Lesson 13 — Decision trees and random forests: a flow chart learned from data

For: Dani (PhishGuard — second model, feature importance)  ·  Time: 45 – 60 min Before: Lessons 01, 03, 12  ·  After this: comparing the two models (Lesson 04 ROC)

🎯 By the end, the student can

  1. Compute Gini impurity and the gain of a split by hand, and say how a tree picks its question.
  2. Explain why a deep tree overfits, with the animation.
  3. Explain the two random ingredients of a forest (bootstrap rows, random features) and why averaging helps.
  4. Read a feature-importance chart — and say what it does not tell you.

1. A tree is a flow chart

Trained on the 20 PhishGuard features. Each box asks one yes/no question; a URL falls down to a leaf and gets the majority class there. Read one path aloud: "digit_ratio > 0.013 and num_digits > 9.5 and num_hyphens ≤ 2.5 → 1,036 URLs, 986 phishing → phishing."

Trees handle what logistic regression cannot: interactions ("hyphens matter only when there are many digits"), and they need no scaling (a threshold is a threshold).

2. How a tree picks the question — Gini impurity

Gini=1−∑kpk2pure group=0,50/50=0.5\text{Gini}=1-\sum_k p_k^2\qquad\text{pure group}=0,\quad 50/50=0.5

For every feature and every threshold: split, compute the weighted Gini of the two children, and keep the split with the biggest gain = Gini(parent) − weighted Gini(children). The guide's example: has_https gives gain 0.18, num_dots > 2 gives 0 → the tree asks about HTTPS first. Then it repeats inside each child (recursion).

3. Watch a tree overfit

(Toy 2-D data — two real URL features overlap too much to see anything.) Depth 1: one cut. Depth 5: a sensible shape. Unlimited depth: 101 leaves, tiny boxes around single points — 100 % on training, worse on test (0.89 → 0.85). The brakes: max_depth, min_samples_leaf — chosen by cross-validation.

4. A random forest — many trees, one vote

Breiman (2001): grow many deep trees, each one

  1. on a bootstrap sample — N rows drawn with replacement (some twice, about a third not at all);
  2. choosing each split among a random subset of features.

Each tree is wrong in its own way; their mistakes are different, so the average of their votes cancels much of it.

Analogy — the wisdom of crowds: guess the number of sweets in a jar. Individuals are far off; the average of the class is usually close — as long as they guessed independently. The two random ingredients are what make the trees independent.

5. Feature importance

How much each feature reduced Gini, summed over all trees (here: test accuracy ≈ 0.85 with default settings). Dani's chart feature_importance.png.

⚠️ What importance does not say: the direction (does a high value mean phishing or legitimate?), or the reason for one URL. That's why PhishGuard's explainer for the forest is an honest approximation (importance × sign(scaled value)) while for logistic regression it is exact.

6. Misconceptions

Student says Truth
"A tree with 100 % training accuracy is perfect" It memorised. Look at the test curve.
"A forest is one big tree" Many independent trees + a vote.
"More trees can overfit" Adding trees doesn't overfit; it just costs time. Depth / leaf size is what overfits.
"Importance = the feature causes phishing" Correlation in this data, nothing more. Correlated features also share importance.

  1. 20 questions (5 min). One student thinks of an animal; the class asks yes/no questions. Which first question splits best? That is Gini gain.
  2. Build a tree by hand (15 min). 10 cards (URL features + label). Groups compute the Gini gain of 3 candidate splits, choose the best, recurse once.
  3. Crowd wisdom (5 min). Jar of sweets; collect guesses; compare the average with the truth.
  4. In 25_PhishGuard/02_examples/02_models.ipynb, set max_depth=None for one tree and compare train/test accuracy.

1. A group has 8 phishing and 2 legitimate URLs. Gini?

2. Why does every tree in the forest get a different sample of rows?

So the trees make different mistakes. Identical trees would vote identically, and averaging would change nothing.

3. Does the random forest need the StandardScaler?

No — splits are thresholds, unaffected by scaling. It is harmless to keep it in the pipeline for a uniform interface, and the explainer uses the scaled value's sign.

Lesson 14 — The SVM, calibration, and comparing two models honestly

For: Laith (SpamClassifier stage 5)  ·  Time: 45 min Before: Lessons 02, 04, 05, 11  ·  After this: the comparison chapter of Laith's book

🎯 By the end, the student can

  1. Explain the SVM as "the widest street between the classes", and what support vectors are.
  2. Explain the C parameter with the animation.
  3. Explain why a raw SVM output is not a probability, and what Platt calibration does.
  4. Compare NB and the SVM fairly (same split, same threshold rule) and explain why NB stays the primary model.

1. The widest street

Many lines separate the training data. The SVM chooses the one with the largest margin — the widest "street" with no points inside. Intuition: a line far from both classes is the safest bet for new points.

Only the points on the edge of the street — the support vectors — decide where the line is. All the others could move (without crossing the street) and nothing would change.

2. Real data is not separable — the C parameter

Real classes overlap, so some points must be inside the street or on the wrong side. C is the price of each mistake:

C street training mistakes risk
small wide many allowed underfitting, very stable
large narrow few allowed overfitting to noise

Choose C by grid search inside cross-validation (Lesson 05) — never on the test set.

3. Generative vs discriminative

Naive Bayes SVM
learns how each class generates words (P(w | c)) only where the boundary is
training counting, one pass optimisation
needs scaling no (counts) yes — StandardScaler first (the 7 handcrafted features would otherwise dominate)
explanation exact: each word's log-odds approximate after calibration

4. Calibration — from distance to probability

LinearSVC returns a signed distance from the line ("2.3 = well inside the spam side") — not a probability, and not comparable to NB's 0.94. Platt scaling fits a sigmoid (a 1-feature logistic regression, Lesson 12) from distance to label, on held-out folds:

base = make_pipeline(StandardScaler(), LinearSVC(C=self.c, random_state=config.RANDOM_SEED))
self._model = CalibratedClassifierCV(base, method="sigmoid", cv=5)

Right panel: Naive Bayes' probabilities are almost only 0 or 1 (the naive assumption multiplies evidence as if it were independent → overconfident). The calibrated SVM uses the whole range. Both rank well; only calibrated numbers can share a threshold.

5. The fair comparison

Same validation split, same rule (precision ≥ 0.98, best recall — Lesson 04). In this quick run the two are almost equal (recall ≈ 0.89 vs 0.88). Fair means: same data split, same preprocessing, the scaler and C chosen inside CV, both calibrated, one threshold rule. Report the numbers on the test set once.

Why NB stays primary even if the SVM were a little better: the project requires an exact reason for every verdict. NB's explanation is the model; the SVM's, after calibration, is an approximation.

6. Misconceptions

Student says Truth
"The SVM gives a probability" It gives a distance. Calibration makes a probability.
"Higher C is always better — fewer training errors" Fewer training errors; often more test errors.
"Calibration changes which messages are spam" It is monotonic: the ranking is unchanged. It changes the numbers, so a shared threshold makes sense.
"Comparing on different splits is fine" Then you compare luck, not models.

  1. The street (10 min). Coloured counters on a table (two colours). Students lay a ruler as the "line" and two pencils as the street edges; widest street wins. Which counters touch the pencils? (support vectors)
  2. Predict-then-run (5 min). "What happens to the street when C grows?" — then play the GIF.
  3. Weather forecaster (5 min). "70 % rain" — on how many of those days should it rain? That's calibration.

Nothing. The solution depends only on the support vectors.

2. Why does the SVM need StandardScaler but Naive Bayes doesn't?

The SVM measures distances/margins in feature space, so a feature with large numbers (message_length in the thousands) would dominate. NB multiplies per-word probabilities from counts — no distances.

3. Why `CalibratedClassifierCV(..., cv=5)` and not calibrate on the training predictions?

On its own training data the SVM is overconfident; the sigmoid would learn that. Held-out folds give honest distances.

Lesson 15 — k-nearest neighbours: "tell me who your neighbours are"

For: Seif (WineGrader stage 4 — the heart of the project)  ·  Time: 2 × 45 min Before: Lessons 02, 03, 05  ·  After this: Lesson 16 (kd-tree), Lesson 17 (feature weights)

🎯 By the end, the student can

  1. Explain k-NN in one sentence and run it by hand on a small table.
  2. Compute a weighted Minkowski distance (p = 1 and p = 2), and explain why the root can be skipped for ranking.
  3. Compute the weighted vote and its confidence, and apply the imbalance correction with alpha.
  4. Explain with pictures what a small and a large k do.

1. The idea

To grade a new wine, find the k most similar wines we already graded and let them vote. There is no training — the "model" is the stored data (a lazy learner). All the work happens at prediction time.

Two of the 11 features (alcohol and volatile acidity, z-scored). The star is a new wine; the dashed circle grows as k grows; on the right, the weighted vote. Watch the answer change with k: k = 1 says high (one very close high wine), k = 15 says medium.

2. Distance

d(a,b)=(∑iwi|ai−bi|p)1/pp=1 Manhattan,p=2 Euclidean,wi=feature weightd(a,b)=\Big(\sum_i w_i\,|a_i-b_i|^p\Big)^{1/p}\qquad p=1\text{ Manhattan},\ p=2\text{ Euclidean},\ w_i=\text{feature weight}

By hand, p = 2, weights 1: a = (0, 0), b = (3, 4) → (9 + 16)^½ = 5. With p = 1: 3 + 4 = 7.

Skip the root for the search: if 25 < 36 then 5 < 6 — the order is the same. Seif's minkowski_power ranks; minkowski (with the root) is only computed for the k winners (test_skipping_the_root_keeps_the_order).

⚠️ Scale first (Lesson 02) — otherwise total SO₂ decides every distance.

3. The weighted vote

vote=1d+εconfidence=winner’s votesall votes\text{vote}=\frac{1}{d+\varepsilon}\qquad\text{confidence}=\frac{\text{winner's votes}}{\text{all votes}}

The guide's example (left): one high wine at 0.10 votes 10.0; two medium wines at 0.90 and 1.00 vote 1.1 + 1.0 = 2.1 → HIGH, confidence 10.0 / 12.1 = 0.83. Without weights, the two far wines would outvote the almost identical one.

4. The imbalance correction (alpha)

44 % of wines are medium, 19 % high: in a mixed neighbourhood, medium wins by numbers alone. Divide each vote by its grade's share raised to alpha:

vote=1/(d+ε)prior[grade]α\text{vote}=\frac{1/(d+\varepsilon)}{\text{prior}[\text{grade}]^{\alpha}}

Right panel: neighbours medium, medium, high (all at distance 1). alpha = 0 → medium 2.0 vs high 1.0. alpha = 1 → medium 2/0.44 = 4.5 vs high 1/0.19 = 5.3 → HIGH.

5. Choosing k and alpha — the real curves

k behaviour
1 islands around single wines — one mislabelled wine causes an error every time
15–25 local and smooth
151 not local any more — almost everything becomes medium

On the real data (5,320 unique wines, 11 features, 5-fold): macro-F1 rises from 0.54 (k = 1) to ≈ 0.58 around k = 21 and then stays flat. alpha trades: macro-F1 stays about the same up to ≈ 0.4–0.5 while the recall of high wines rises from 0.45 to ≈ 0.6 — which is why Seif's tuning rule prefers alpha = 0.5 (theory §4.5: 0.585 vs 0.586, recall 0.45 → 0.61).

6. Ties

Two grades with exactly the same votes: np.argmax would always pick the lower grade number — an arbitrary bias toward low. The project's rule: the grade of the nearest neighbour among the tied grades wins — deterministic and meaningful.

7. Proving it is right

test_knn_matches_sklearn runs your k-NN and KNeighborsClassifier(weights="distance") on the same 400 training points and 200 queries, for p = 1 and p = 2, and demands identical answers. If it fails, compare the neighbours first (the index), then the votes.

Student says Truth
"k-NN trains a model" It stores the data. fit = remember (and the scaler).
"k = 1 is the most accurate, it uses the closest wine" It is the most noisy. Tasters disagree; one wine is not evidence.
"Bigger k is safer" Too big = the majority class everywhere.
"The prior of a missing class is 0" 1.0 — 0 ** alpha would divide by zero. (Seif's FAQ in theory §4.5.)

Lesson 16 — The kd-tree: skipping work, and when skipping stops working

For: Seif (WineGrader stage 5)  ·  Time: 60 min Before: Lesson 15; recursion; Python's heapq  ·  After this: the "measure and decide" chapter of the book

🎯 By the end, the student can

  1. Build a kd-tree by hand on paper (widest axis, middle position, leaf size).
  2. Run the search with pruning and explain the gap test that makes skipping safe.
  3. Explain the max-heap trick with negated keys.
  4. Explain the curse of dimensionality with two pictures, and defend "I built it and then didn't use it".

1. The problem

Linear search measures the distance to every training wine (~4,250). Can we skip wines that obviously cannot be among the nearest? Like looking for a house: you don't measure the distance to every house in the country — you go to the right city, then the right street.

2. Building: cut the box in half, again and again

  1. If ≤ leaf-size points remain (Seif: 16; here 8 to see it), stop → leaf.
  2. Choose the axis with the largest spread (× its weight — a weight-0 feature is never worth cutting).
  3. Sort by it, cut at the middle position: first half left, second half right; the value there is the threshold.
  4. Recurse on each half.

Why the middle position, not "< median goes left"? Repeated values: if 300 wines share the same pH, "< median" can send them all to one side and the recursion never ends. The middle position always halves.

3. Searching: go near first, then ask "could the far side matter?"

Keep the k best so far (orange rings; dashed circle = the k-th best distance). At each node:

  1. go to the near side first (where the query is);
  2. coming back, compute the gap — the distance from the query to the cutting line along that one axis. Every point on the far side is at least that far away:

gap=waxis⋅|qaxis−threshold|p\text{gap}=w_{axis}\cdot|q_{axis}-\text{threshold}|^{p}

  1. if gap > k-th best distance → skip the whole far box (grey) without measuring anything inside it.

Here: 35 of 160 distances computed for k = 5.

search(near)
gap = w[axis] * abs(diff) ** p
if len(heap) < k or gap <= worst_distance_in_heap:   # <= : ties must still be reachable
    search(far)                                      # otherwise: skipped entirely

4. The heap trick

We need instant access to the worst of the k best (to compare with the gap and to replace it). Python's heapq is a min-heap → store (-distance, -row): the smallest negated value is the largest distance, so heap[0] is the worst kept wine. (-row makes ties come out like the linear search.)

5. Correctness first

A tree that prunes one branch too many still returns k wines — just not the nearest — and nothing else would notice. So test_kdtree_matches_linear asks both indexes for 1,000 random queries (uniform and mixed weights including zeros, p = 1 and 2) and demands identical answers.

6. The curse of dimensionality

Left: with random points, the farthest point is 10,000× farther than the nearest in 1-D, but only 1.5× in 100-D — "near" and "far" stop meaning much, so the k-th best distance stays big and the gap test rarely wins.

Right (real wines, k = 20, leaf 16): with the 2 features most correlated with quality the tree measures 2 % of the wines; with all 11 it measures 59 %. (Seif's guide: 2 % → 54 % with his 12 features; with Python overhead the tree is then ~10× slower than numpy doing everything at once.)

Two reasons, both for the defence:

  1. Too few cuts per axis — 4,000 points / leaf 16 ≈ 8 levels ≈ 8 cuts in total. In 2-D that's 4 per axis; in 12-D some axes are never cut, the boxes are long slabs, and the "far side" is rarely far.
  2. Distances concentrate (left panel).

That is why config.DEFAULT_INDEX = "linear": the measurement decided it.

❓ "You built a kd-tree and didn't use it — wasted work?" No: the claim is "here is how to decide whether it helps". It is implemented, proven correct, measured, and the dimension curve explains the result. For a 4-feature model the same code wins by a factor of ten.

7. Misconceptions

Student says Truth
"The kd-tree is approximate" It is exact — pruning only skips boxes that provably can't contain a better point.
"A tree is always faster than a list" Not in high dimensions, and not against vectorised numpy. Measure.
"Prune with <, it's the same" <= keeps ties reachable so results equal the linear search exactly.

  2. Search by hand (10 min). Mark a query; find the 1-NN. Count how many dots you measured. Who measured fewest?
  3. Measure (10 min). In 32_WineGrader/02_examples/03_kdtree.ipynb, change the number of features and time both indexes.

1. The query is at x = 3.0; the cut is at x = 2.0; p = 2, weight 1; the current k-th best power distance is 0.8. Search the far side?

gap = |3 − 2|² = 1.0 > 0.8 → skip it.

2. Why multiply the spread by the feature weight when choosing the axis?

A feature with weight 0 adds nothing to any distance, so cutting on it could never prune anything. Weighted spread picks the axis that matters for the distance.

3. Why does a heap store (−distance, −row) instead of (distance, row)?

heapq is a min-heap; negating makes heap[0] the largest distance = the worst of the k best, which is what we compare and replace.

Lesson 17 — Learning a weight per feature: coordinate search and the incremental update

For: Seif (WineGrader stage 6)  ·  Time: 45 – 60 min Before: Lessons 05, 15  ·  After this: the tuning / results chapter of the book

🎯 By the end, the student can

  1. Explain what a feature weight does to the distance (and that weight 0 = feature removed).
  2. Explain why gradient descent cannot be used here, with the staircase picture.
  3. Run coordinate search by hand: try ×0, ×0.5, ×1.5, ×2; keep only improvements > 0.002; stop when a pass changes nothing.
  4. Explain the incremental update D_new = D + (w_new − w_old)·|Δᵢ|ᵖ and why it is correct.
  5. Report an honest "it did not help" result.

1. What a weight is

d(a,b)=(∑iwi|ai−bi|p)1/pd(a,b)=\Big(\sum_i w_i|a_i-b_i|^p\Big)^{1/p}

Weight 2 on alcohol: one standard deviation of alcohol counts like two. Weight 0 on pH: pH is ignored. Learning the weights = letting the data decide which features matter for "similar wine". (Remember the slider in Lesson 02.)

2. Why not gradient descent?

Nudge a weight a little: either no neighbour changes (score exactly the same — slope 0) or one neighbour swaps (score jumps). There is no slope to follow — gradient descent (Lessons 12, 21) has nothing to work with. We need a method that only compares scores.

3. Coordinate search — one knob at a time

w = all ones
repeat (at most 3 passes):
    for each feature i (that is not already 0):
        for factor in (×0, ×0.5, ×1.5, ×2):
            score = cross-validated macro-F1 with w[i] · factor
            if score > best + 0.002:  accept it, go to the next feature
    if a whole pass changed nothing: stop                 (early stopping, patience 1)

Analogy: tuning an old radio with several knobs — turn one, listen; keep it if it's clearer; move to the next knob.

  • Why the 0.002 tolerance? One wine changing grade moves macro-F1 by ≈ 0.001. Accepting smaller "improvements" means fitting which wines happen to be in which fold — noise.
  • ×0 removes a feature for good: feature selection for free. (In the animation, chlorides is removed.)

4. Making it fast — the incremental update

Every trial needs all test-to-train distances of every fold. Recomputing from scratch: ~2.8 s per trial × ~100 trials × 5 nested runs — far too slow. The insight: the distance (before the root) is a sum over features, so changing one weight changes the matrix by one term only:

Dnew=D+(wnew−wold)⋅|Δi|pD_{new}=D+(w_{new}-w_{old})\cdot|\Delta_i|^p

One matrix addition instead of eleven. Seif's run fell from ~5 minutes to ~20 seconds. A fast version you can't trust is worthless: test_incremental_matches_full_recompute checks the final score equals a full recompute (the script prints both: 0.5676 = 0.5676).

5. Callbacks — the Observer pattern

The loop doesn't know about files or stopping rules. After each round it calls on_round_end(round, score, weights) on every callback: HistoryLogger (the convergence plot), Checkpoint (best weights to a .tmp file, then rename — a crash never leaves half a file), EarlyStopping. Same idea as Keras callbacks.

6. The honest result

weights nested macro-F1 (real data, Seif's guide)
uniform 0.583 ± 0.018
learned 0.579 ± 0.015

Inside the inner folds learning helped a little (0.581 → 0.585); on the untouched outer folds the gain disappeared. That is overfitting to the inner folds, in miniature — exactly what nested CV (Lesson 05) exists to reveal. Once the features are scaled, no wine feature is useless or dominant enough for reweighting to help. On data with pure-noise features (the test with two noise columns) the same code finds and removes them.

7. Misconceptions

Student says Truth
"The learned weights are better, the inner score went up" Only the outer (nested) score counts.
"Try every combination of weights" 4¹¹ ≈ 4 million combinations × CV — impossible. Coordinate search tries ~50–100.
"The incremental update is an approximation" It is exact (a sum changes by exactly one term). The test proves it.

8. Activities

  1. Radio knobs (5 min). Three volume sliders on a web page / phone mixer: tune one at a time to match a target sound.
  2. Paper update (10 min). Give a 2×3 distance matrix D and the matrix |Δ₂|²; students compute D for w₂ = 0.5 by the update, then by recomputing — same numbers.
  3. Noise test (10 min). Add two random columns to the wine data in the notebook; run coordinate search; watch their weights go to 0.

9. Check yourself

1. D = 2.0 between two wines with weights all 1; the pH term |Δ|² is 0.5. What is D after setting pH's weight to 0?

2.0 + (0 − 1)·0.5 = 1.5.

2. Why does coordinate search never "un-remove" a feature?

×0.5, ×1.5, ×2 of 0 is still 0. Removed stays removed — a deliberate, simple rule.

No — the difference is a fifth of the fold-to-fold spread: a tie. The conclusion is "reweighting doesn't help on this data", and why.

1. Anatomy of a URL

  2. the feature names and order saved inside the model bundle;
  3. a check on load (ModelBundle.load) — plus test_same_url_same_features.

1. Zoom in until you see numbers

(The lessons draw their own faces: FER-2013 pictures may not be redistributed.) A 48 × 48 grey face is 2,304 numbers; 0 = black, 255 = white. The network never "sees a face" — it sees this table.

2. Colour = three tables — and the BGR trap

A colour picture has a red, a green and a blue table. OpenCV stores them as B, G, R. Show a camera frame with matplotlib or Tkinter without cv2.cvtColor(frame, cv2.COLOR_BGR2RGB) and blue faces appear. FaceEmotion converts every face to one grey channel (cv2.COLOR_BGR2GRAY) — colour doesn't tell us the emotion, and 1 channel = 3× less work.

3. Normalisation

pixel / 255.0               → 0 … 1
(x − 0.5013) / 0.2916       → mean ≈ 0, std ≈ 1          (Lesson 02: z-score)

By hand: pixel 200 → 200/255 = 0.784 → (0.784 − 0.5013)/0.2916 = 0.97. Pixel 30 → 0.118 → −1.31.

0.5013 and 0.2916 are the mean and std of all FER-2013 training pixels after equalisation. They live in config.py and are used everywhere. Use other numbers with the camera and the network gets values it never saw — accuracy collapses with no error message (train/serve skew, the same bug as Lesson 18).

4. Histogram equalisation

A face in bad light has all its pixels squeezed into a narrow range (here 20…81). Equalisation maps every grey level through the cumulative histogram (middle): crowded ranges are stretched, empty ranges skipped. Result: the pixels spread over 0…255 — the dark face looks like a well-lit one.

hist = np.bincount(img.ravel(), minlength=256)
cdf  = hist.cumsum()
lut  = round((cdf − cdf_min) / (N − cdf_min) × 255)       # what cv2.equalizeHist does
new  = lut[img]

⚠️ It is pre-processing, so it must happen in training and in real time. That is why Ryan's dataset.py has an EqualizeHist transform in both build_train_transform and build_eval_transform, and test_eval_transform_matches_realtime_preprocessing checks a face becomes the same numbers on both paths. (This was a real bug fixed in the project in October 2026.)

Lesson 20 — A neural network from zero: neurons, layers, softmax, cross-entropy

For: Ryan (FaceEmotion stage 3)  ·  useful background for everyone  ·  Time: 2 × 45 min Before: Lessons 12 (sigmoid, log-loss), 19  ·  After this: Lesson 21 (how it learns), 22 (convolution)

🎯 By the end, the student can

  1. Compute one neuron's output by hand (weights, bias, ReLU).
  2. Explain why a network needs layers and a non-linear activation between them.
  3. Compute softmax and the cross-entropy loss for 3 classes by hand.
  4. Explain why forward() returns logits and not probabilities.

1. One neuron

Ryan's guide, by hand: inputs (0.5, −1.0, 2.0), weights (0.8, 0.3, −0.4), bias 0.1 → z = 0.4 − 0.3 − 0.8 + 0.1 = −0.6 → ReLU(−0.6) = 0. It is logistic regression (Lesson 12) with a different squash at the end.

2. Activation functions

A layer is "weights × inputs + bias". Two layers in a row without anything between them = one bigger linear function — no gain. A non-linear activation between layers is what lets the network bend its decisions. EmotionNet uses ReLU: cheap, and its slope is just 1 (positive) or 0 (negative).

3. Why layers?

One neuron can only draw a straight line. A hidden layer of 4 ReLU neurons can draw a few straight pieces; two layers of 32 can follow a curve. Each layer builds new features from the previous layer's features — in a face network: edges → eyes and mouth corners → whole expressions (Lesson 22).

4. Watch a forward pass

Numbers flow left to right. Each circle = weighted sum of the previous layer + bias, then ReLU (many become exactly 0). The last layer gives one number per class; softmax turns them into probabilities that add up to 1.

5. Softmax — from scores to probabilities

pi=ezi∑jezjp_i=\frac{e^{z_i}}{\sum_j e^{z_j}}

The guide's example: z = (2.0, 0.5, −1.0) → e^z = (7.39, 1.65, 0.37), sum 9.41 → p = (0.785, 0.175, 0.039).

  • exponentiate → everything positive, bigger scores grow much faster;
  • divide by the sum → the numbers add up to 1.

6. Cross-entropy — how wrong were we?

L=−lnptrue classL=-\ln p_{\text{true class}}

Truth = class 1 → L = −ln 0.175 = 1.743. If the network had said 0.9 → L = 0.105. It is the multi-class version of Dani's log-loss (Lesson 12).

During training the "happy" logit is pushed up, its probability rises, the loss falls toward 0.

The elegant result (for the defence): for softmax + cross-entropy, the gradient with respect to the logits is simply

∂L∂z=p−ye.g. (0.785,0.175−1,0.039)=(0.785,−0.825,0.039)\frac{\partial L}{\partial z}=p-y\qquad\text{e.g. }(0.785,\,0.175-1,\,0.039)=(0.785,\,-0.825,\,0.039)

That is why PyTorch joins them in one layer (nn.CrossEntropyLoss takes logits) and why Ryan's forward() returns logits; the predictor applies softmax only for display.

7. Misconceptions

Student says Truth
"Softmax in forward() and CrossEntropyLoss — double safe" Double softmax: wrong loss, slow learning. CrossEntropyLoss applies it itself.
"A probability of 0.9 means the model is right 90 % of the time" Only if it is calibrated (Lessons 14, 24).
"More neurons = always better" More capacity = more overfitting risk and slower real time (EmotionNet: 4.9 M weights, chosen for 25 fps).
"ReLU(−0.6) is −0.6" 0. Negative in → 0 out.

  3. TensorFlow Playground (10 min). Spiral dataset: 0 hidden layers vs 2 hidden layers of 8 neurons; ReLU vs linear.

(⅓, ⅓, ⅓); loss = −ln ⅓ = 1.099 — the loss of pure guessing among 3 classes. For 7 emotions: ln 7 = 1.946 (a useful number to recognise at the start of training).

3. Why can't we stack linear layers without an activation?

W₂(W₁x + b₁) + b₂ = (W₂W₁)x + (W₂b₁ + b₂) — one linear layer again.

Lesson 21 — How a network learns: backpropagation, optimisers, the learning-rate schedule

For: Ryan (FaceEmotion stage 4 — the training loop)  ·  Time: 2 × 45 min Before: Lessons 12 (gradient descent), 20  ·  After this: Lesson 24 (training in practice)

🎯 By the end, the student can

  1. Do a full forward pass, backward pass (chain rule) and update by hand on the guide's tiny network.
  2. Say what loss.backward(), optimizer.step() and optimizer.zero_grad() each do.
  3. Explain the effect of the learning rate with the animation.
  4. Explain momentum and Adam(W) in one sentence each, and the warm-up + cosine schedule.

1. Backpropagation with numbers

The guide's network: one input, one hidden ReLU neuron, one output, squared loss.

FORWARD     x = 2, w1 = 0.5, b1 = 0, w2 = −1, b2 = 1, target t = 1
            z1 = 0.5·2 + 0 = 1.0     h = ReLU(1.0) = 1.0     y = −1·1 + 1 = 0.0     L = (0 − 1)² = 1.0

BACKWARD    dL/dy  = 2(y − t)  = −2
            dL/dw2 = −2 · h    = −2         dL/db2 = −2
            dL/dh  = −2 · w2   =  2
            dL/dz1 = 2 · 1     =  2         (ReLU's slope is 1 because z1 > 0)
            dL/dw1 = 2 · x     =  4         dL/db1 = 2

UPDATE      lr = 0.1:  w1 = 0.1, b1 = −0.2, w2 = −0.8, b2 = 1.2
            new forward: y = 1.2, L = 0.04          ← from 1.0 to 0.04 in one step

The chain rule in one sentence: how much L changes when w1 moves = (how L changes with y) × (how y changes with h) × (how h changes with z1) × (how z1 changes with w1). Backprop computes these products from the end to the start, reusing each one — that's why it's fast even for 4.9 million weights.

In PyTorch — the three lines of every training step:

optimizer.zero_grad()      # forget the previous batch's gradients (they ADD UP otherwise)
loss.backward()            # backprop: fill .grad of every weight
optimizer.step()           # update: w = w − lr · (something made from .grad)

⚠️ Notice h became exactly 0 after the update. If z1 goes negative, ReLU's slope is 0 and that neuron stops learning ("dead ReLU") — one reason for BatchNorm before ReLU and a gentle start (warm-up).

2. The learning rate

Too small: crawls (wasted epochs). Good: walks into a valley and settles. Too big: jumps over valleys, the loss goes up and down — or explodes to nan. Also note: gradient descent finds a valley, not necessarily the deepest one. In big networks that turns out to matter much less than you'd fear.

3. Better than plain steps: momentum and Adam

A long narrow valley with noisy gradients (each mini-batch gives a slightly different gradient):

optimiser idea in the animation
SGD w −= lr·g crawls along the valley floor
momentum keep a running average of the gradients — a heavy ball keeps rolling overshoots, then speeds along
Adam momentum and divide each weight's step by its typical gradient size heads for the minimum; every weight gets a sensible step

AdamW (Ryan's optimiser) = Adam + weight decay applied directly (w −= lr·λ·w, λ = 1e-4): pulls every weight a little toward 0 each step, against memorising.

4. The learning-rate schedule

warm-up (epochs 1–3):    lr = lr_max · (0.1 + 0.9 · t/3)
cosine (epochs 4–50):    lr = 0.5 · lr_max · (1 + cos(π · t/47))

At the start the weights are random and the gradients wild — small steps avoid wrecking them (and dead ReLUs). In the middle, big steps cover distance. At the end, tiny steps settle into the minimum instead of shaking around it. Cosine is smooth: no "when to drop" hyper-parameter.

5. Mini-batches and epochs

word meaning (FaceEmotion)
batch 128 faces; the gradient is the average over them
step one zero_grad → backward → step
epoch one pass over all 28,709 training faces ≈ 225 steps

Why not the whole dataset per step? Too slow and too much memory. Why not one face? Too noisy. A batch is the compromise — and its noise even helps escape bad valleys.

6. Misconceptions

Student says Truth
"backward() updates the weights" It only computes gradients. step() updates.
"I can skip zero_grad()" Gradients accumulate → each step uses the sum of all previous batches.
"Loss went to nan, the data is broken" Usually the learning rate is too high (or a log of 0). Lower it first.
"Adam doesn't need a learning rate" It does; it's just less sensitive to it.

  1. The chain on paper (20 min). Repeat the worked example with x = 1 (everything else the same). (z1 = 0.5, h = 0.5, y = 0.5, L = 0.25; dL/dy = −1, dL/dw2 = −0.5, dL/dw1 = 1·1·x = 1 …)
  2. Heavy ball (5 min). Roll a marble and a ball bearing down a bent ruler — which one gets past a small bump? That's momentum.
  3. Break it (10 min). In 13_FaceEmotion/02_examples/03_training_loop.ipynb: set lr = 1.0, remove zero_grad(), forget eval() — observe each failure.

8. Check yourself

1. In the worked example, why is dL/dh = −2 · w2?

y = w2·h + b2, so dy/dh = w2. Chain rule: dL/dh = dL/dy · dy/dh = −2 · (−1) = 2.

2. The training loss goes down, the validation loss goes up. Is the optimiser broken?

No — that's overfitting (Lessons 01, 24). The optimiser is doing its job on the training data too well.

3. Why does Adam divide by sqrt(v)?

v tracks each weight's typical squared gradient. Dividing normalises the step: weights with huge gradients get relatively small steps and vice versa — so one global lr works for all 4.9 M weights.

Lesson 22 — Convolution: a small filter that slides over the picture

For: Ryan (FaceEmotion — EmotionNet)  ·  Time: 45 – 60 min Before: Lessons 19, 20  ·  After this: Lesson 23 (ResNet)

🎯 By the end, the student can

  1. Compute a convolution by hand (one output number = 9 products added up).
  2. Say what a feature map is, and what output size a 3 × 3 filter gives (with and without padding, with stride 2).
  3. Explain max-pooling, and why CNNs use far fewer weights than a dense layer.
  4. Explain the receptive field and why deep layers "see" whole expressions.

1. Why not a normal (dense) layer?

A dense layer from 2,304 pixels to 512 neurons has 1.2 million weights and must learn "an eye" separately for every position. A convolution filter is shared over the whole picture: one 3 × 3 eye-corner detector (9 weights) works everywhere.

2. Watch a filter slide

At each position: multiply the 9 pixels under the filter by the 9 weights, add them up, write one number. The filter (−1 0 +1 in each row) answers "is it brighter on the right than on the left?" → big numbers exactly along the vertical edge, 0 on flat areas.

By hand, top-left of the edge: pixels 0 0 9 / 0 0 9 / 0 0 9, filter −1 0 1 ×3 → (0·−1 + 0·0 + 9·1) × 3 rows = 27.

sizes 48 × 48 input, 3 × 3 filter
no padding 46 × 46 (we lose a border)
padding=1 (EmotionNet) 48 × 48 — same size
stride=2 24 × 24 — the filter jumps 2 pixels; halves the size

3. What filters find

Edge filters light up outlines (eyes, mouth, face contour); blur averages; sharpen exaggerates differences. In a CNN nobody writes these by hand — the first layer of EmotionNet has 64 filters learned by gradient descent, and they turn out to look much like edge and blob detectors.

With several input channels (e.g. 64 feature maps in), each filter is 3 × 3 × 64 and sums over all of them.

4. Pooling and stride — making the picture smaller

Max-pool keeps the strongest response in each 2 × 2 block: 4× fewer numbers, and a feature that moves by one pixel gives the same answer. EmotionNet shrinks with stride-2 convolutions instead (48 → 24 → 12 → 6), then global average pooling at the end (each of 512 maps → one number).

5. The receptive field

One unit in a deep layer depends on a growing window of the input: 3, 5, 7 … pixels with plain 3 × 3 layers, much faster with stride 2. Early layers see edges; middle layers see eyes, mouth corners; the last layers see the whole face — an expression.

6. Misconceptions

Student says Truth
"Each position has its own filter" One filter, shared everywhere — that's the point.
"The CNN looks for faces I programmed" It learns its filters from data.
"Pooling loses information, so it's bad" It deliberately throws away exact positions to gain tolerance and speed.
"A 3 × 3 filter only sees 3 × 3" In layer 1. Stacked layers see more (receptive field).

3. Why does EmotionNet end with global average pooling instead of flattening 512 × 6 × 6?

2. The problem ResNet solved — vanishing gradients

Before 2015, a 56-layer network trained worse than a 20-layer one — even on training data. Backprop multiplies one factor per layer; many factors < 1 → almost nothing reaches the first layers (red). With shortcuts the gradient has a direct path back (green).

3. The residual block

out=ReLU(F(x)+x)\text{out}=\text{ReLU}\big(F(x)+x\big)

  • The layers learn only the correction to x. If nothing is needed, F(x) = 0 and x passes through unchanged.
  • When the block halves the picture (stride 2) or changes the channels (64 → 128), x has the wrong shape to add → the shortcut becomes a 1 × 1 conv with stride 2 + BN that only matches the shape (test_residual_block_halves_with_stride_two).
identity = self.shortcut(x)            # nn.Identity() or 1x1 conv + BN
out = F.relu(self.bn1(self.conv1(x)))
out = self.bn2(self.conv2(out))
out = F.relu(out + identity)           # the jump

4. BatchNorm

For every channel, over the batch: subtract the mean, divide by the std (Lesson 02 again — inside the network), then let the network rescale with learned γ, β. Keeps every layer's inputs in a healthy range → faster, more stable training, higher learning rates possible. During training it also keeps running averages of mean and variance.

5. Dropout

In training, each batch randomly switches off 30 % of the neurons before the last layer (the rest are multiplied by 1/0.7). No neuron can rely on another — the network learns redundant, robust features. 0 parameters.

6. model.train() vs model.eval() — the most-asked question

train() eval()
Dropout random 30 % off everyone on
BatchNorm normalises with this batch's mean/var, updates running averages uses the running averages

eval() does not "evaluate" anything — it is a switch. Forget it in real time and: Dropout makes every frame random, and BatchNorm normalises one face by itself (variance 0) → nonsense. Always: model.eval() + torch.no_grad() for inference.

Lesson 25 — Finding the face: Haar features, the integral image and the cascade

For: Ryan (FaceEmotion stage 2)  ·  Time: 45 min Before: Lesson 19  ·  After this: Lesson 26 (real time)

🎯 By the end, the student can

  1. Explain a Haar feature (white sum − black sum) and point at two on a face.
  2. Build an integral image by hand and get any rectangle's sum with 4 reads.
  3. Explain the cascade with its arithmetic (0.995²² vs 0.5²²) and why it is fast.
  4. Explain scaleFactor, minNeighbors and minSize.

1. Two networks, two jobs

The emotion network (Lessons 20–24) needs a 48 × 48 face. The camera gives a 640 × 480 room. Step one is to find the face — with an algorithm from 2001 (Viola–Jones) that is still excellent for frontal faces, and runs in milliseconds.

2. Haar features

A Haar feature = sum of pixels in the white rectangle − sum in the black rectangle. "The eye band is darker than the cheeks" is a two-rectangle feature; "the bridge of the nose is brighter than the eyes" is a three-rectangle feature. One feature alone is weak — but cheap, and thousands of them, chosen well, are strong.

3. The integral image — any rectangle in 4 reads

Each cell of the integral image holds the sum of everything above and to the left of it. Then for any rectangle:

sum=I(D)−I(B)−I(C)+I(A)\text{sum}=I(D)-I(B)-I(C)+I(A)

The guide's example: picture 1 2 3 / 4 5 6 / 7 8 9 → integral 1 3 6 / 5 12 21 / 12 27 45. Rectangle [5 6; 8 9]: 45 − 6 − 12 + 1 = 28 ✓ (5 + 6 + 8 + 9). Same cost for a 2 × 2 or a 200 × 200 rectangle — that is what makes the detector fast.

4. Sliding windows and the cascade

A window slides over the picture (and again at bigger sizes — scaleFactor = 1.1 grows it 10 % per round). For each window, the cascade asks a few cheap questions first; a window that fails is rejected immediately (red). Only the survivors are asked more. In this toy run: 1,125 windows → 76 pass stage 1 → 15 reach the end, all on the face.

OpenCV's cascade: ~22 stages, each tuned to keep 99.5 % of faces and drop 50 % of non-faces
    faces surviving all stages:     0.995^22 ≈ 0.90
    non-faces surviving:            0.5^22   ≈ 2.4e-7   →  of 100,000 windows ≈ 0.02 false hits
    work: most windows die in stage 1–2 → ~20–30 features per window instead of 6,000

The idea: don't make each check more accurate — order the checks so the expensive work only happens on the few that reach the end. (Which features, in which order: chosen once by AdaBoost on thousands of pictures; you get the result as an XML file.)

5. minNeighbors — one window is not enough

A real face fires dozens of overlapping windows (shift 2 pixels, slightly bigger — still a face). A false hit usually fires one or two. detectMultiScale groups overlapping windows; minNeighbors = 5 drops groups smaller than 5.

parameter (config.py) meaning too low too high
scaleFactor = 1.1 window grows 10 % per round slow misses sizes in between
minNeighbors = 5 how many windows must agree false faces missed faces
minSize = (60, 60) ignore smaller faces slow, far-away noise misses people far from the camera

Lesson 26 — Real time: the frame budget, the camera thread, and a label that doesn't flicker

For: Ryan (FaceEmotion stage 5) · the threading part also for Liraz (Lesson 32)  ·  Time: 45 min Before: Lessons 23, 25  ·  After this: the real-time chapter of the book

🎯 By the end, the student can

  1. Draw the time budget of one frame and say why the camera read must be in its own thread.
  2. Explain "latest frame only" and why the shared frame needs a Lock and a copy.
  3. Explain temporal smoothing and why it averages probabilities, not labels.
  4. Compute the delay smoothing adds, and defend N = 5.

1. The time budget

25 fps = 40 ms per frame for everything: detection, pre-processing, inference, drawing. The biggest cost is not on the list: cap.read() blocks 30–40 ms until the camera delivers. In the GUI thread that alone would eat the budget — so it runs in its own thread.

2. Latest frame only

The camera thread overwrites one slot with the newest frame; the GUI takes whatever is there. A queue would fill up when the GUI is slower, and the screen would show the past. Two threads, one variable → a threading.Lock, and read() returns frame.copy() (drawing on the shared buffer would corrupt it).

Tkinter is single-threaded: no while True in the GUI. Use root.after(30, process_frame) — process one frame, schedule the next, and the window stays responsive.

3. Why the label flickers — and the fix

Each frame is classified on its own. In a borderline expression (51 % happy / 49 % neutral) one pixel of noise flips the label. Simulation, 100 frames: the raw label changes 20 times (8 per second — flicker); a moving average over the last 5 probability vectors changes it 4 times.

class TemporalSmoother:
    def __init__(self, window=5):
        self._history = deque(maxlen=window)    # the oldest drops out by itself
    def update(self, probs):
        self._history.append(probs)
        return np.mean(self._history, axis=0)   # average the VECTORS, then argmax

4. Average the probabilities, don't vote

Three frames: (0.6 happy, 0.4 sad), (0.6, 0.4), (0.0, 1.0). Voting: happy 2 – 1. Averaging: happy 0.4, sad 0.6. The third frame was very sure; the average respects confidence, voting throws it away. That's test_probabilities_are_averaged_not_voted.

5. The price: delay

A moving average over N frames reacts about N/2 frames late. N = 5 at 25 fps → ≈ 100 ms (people don't notice below ~150 ms). N = 15 → ≈ 300 ms — noticeable. If the success metric ("≤ 2 label changes per second") fails, go to 7, not 15.

"A bigger window is always better" Bigger = slower to react.
"Process every frame from a queue to be correct" Then the screen lags further and further behind. Skip frames instead.

Lesson 27 — Do two stays collide? Half-open intervals and a two-comparison rule

For: Eran (HotelManager stage 1 — "the heart")  ·  Time: 45 min Before: Python date, booleans  ·  After this: Lesson 28 (allocation), Lesson 33 (the SQL version)

🎯 By the end, the student can

  2. Write the overlap rule a < d and c < b and prove it with De Morgan.
  3. Check the rule on all eight cases, and explain why case F breaks careless code.
  4. Explain how a booking's state decides whether it blocks the room.

1. Half-open: we sell nights, not days

Guest 1 checks in on the 2nd and out on the 9th: nights 2, 3, …, 8 → 7 nights = 9 − 2. The 9th is not included — guest 2 can check in that afternoon. Writing a stay as [a, b) (a included, b not) makes this automatic:

  • nights = b − a, no "+1" anywhere;
  • back-to-back stays [2, 9) and [9, 12) don't share anything.

2. The rule

[a,b)and[c,d)collide⇔a<dandc<b[a,b)\ \text{and}\ [c,d)\ \text{collide}\iff a<d\ \text{and}\ c<b

Watch a 3-night stay slide past ours: both lights must be ✓ to collide. The moment its check-in reaches 7 (our check-out), c < b fails → free.

3. All eight cases (from Eran's guide)

Case F is the one careless code gets wrong: with <= instead of <, a guest arriving the day another leaves would be refused — real lost money. tests/test_date_range.py has all eight; F has its own test.

(These are Allen's interval relations, 1983 — 13 possible relations between two intervals; six overlap.)

4. The proof — De Morgan

It is easier to say when two stays are free: theirs ends before ours starts (d ≤ a) or theirs starts after ours ends (b ≤ c). Negate it: NOT(P or Q) = (NOT P) and (NOT Q) → a < d and c < b. Two comparisons replace an if-ladder of eight situations.

5. Checked by brute force

Every pair of stays with dates 1…12: 4,356 pairs, 0 mismatches between the rule and "do they share a night?". Change < to <= in the script and watch case F turn red.

6. From one pair to "is the room free?"

def is_room_free(room_id, stay, bookings, ignore_booking_id=None):     # the sketch - write your own
    for booking in bookings:
        if booking.room_id != room_id or booking.id == ignore_booking_id:
            continue
        if not booking.status.blocks_room:     # cancelled / checked-out bookings are invisible
            continue
        if booking.stay.overlaps(stay):
            return False
    return True

blocks_room is True only for CONFIRMED and CHECKED_IN (Lesson 30) — so cancelling frees the room instantly, with no deletion and no special case. In SQL the same rule becomes WHERE room_id = ? AND check_in < :d AND :c < check_out AND status IN (...) — fast with an index (Lesson 33).

"I need an if for each of the 8 cases" Two comparisons cover all of them.

"Cancel = delete the booking" Change the state; availability ignores it; history is kept.

1. The three rules (the guide's example)

strategy rule Python
First-Fit lowest room number min(cands, key=lambda r: int(r.number))
Best-Fit smallest capacity that fits; tie → cheaper → lower number min(cands, key=lambda r: (r.capacity, r.rate, int(r.number)))

Two Python tricks to explain on the board:

  • A tuple as the key: Python compares tuples left to right — capacity first, then rate, then number. The order is always fully decided → the same request always gets the same room → reliable tests.
  • -int(r.number) inside max: for equal scores we want the smallest number, and −101 > −102.

1. The invoice as a picture

  • Every rule produces visible invoice lines — the guest sees why the price is what it is.
  • A discount is a negative line, not a hidden subtraction; the total is just the sum of the lines (never computed twice in two ways).

4. Open / closed

Adding "returning guests −5 %" = one new class + one line in the engine's list. No other rule, test or file changes. Complexity O(nights × rules) ≤ 30 × 5 = 150 operations.

Money: round each line to the agora (round(x, 2) in Eran's code; this lesson's script uses Decimal with ROUND_HALF_UP, which avoids float surprises like 0.1 + 0.2 = 0.30000000000000004). Whatever you choose, round per line, then sum.

"Order doesn't matter, addition is commutative" The rules read the lines so far — percentages of different bases.
"VAT on the discount line is wrong" VAT is on what the guest actually pays: the lines after the discount.
"The weekend surcharge uses the base rate" It uses the night's (seasonal) price — 675, not 450, in high season.

Lesson 30 — Finite state machines: making illegal moves impossible

For: Eran (the booking life cycle) · Liraz (the game server + scoring)  ·  Time: 45 – 60 min Before: Python Enum, classes  ·  After this: Lesson 32 (Liraz: the FSM under threads), Lesson 33 (transactions)

🎯 By the end, the student can

  1. Define state, event, transition and guard, and draw the FSM of their own project.
  2. Fill a transition table (state × event → new state or error), and write one guarded transition in code.
  3. Explain why an FSM makes the program correct and testable.
  4. (Liraz) Compute the time-based score; (Eran) explain how the state drives availability.

1. What a state machine is

A program that is always in exactly one of a few states, and moves between them only through defined transitions, triggered by events, sometimes only if a guard (condition) is true.

Analogy — a traffic light: red → green → yellow → red. "Red → yellow" does not exist. Nobody needs to remember to check it; there is simply no such arrow.

2. Eran: a booking's life cycle

from event guard action to
CONFIRMED check in today ≥ check-in date stamp the time CHECKED_IN
CHECKED_IN check out — build the invoice (one transaction) CHECKED_OUT
CONFIRMED cancel before check-in compute the fee (0 or 1 night) CANCELLED

Anything else → a clear error saying why ("Cannot cancel: the guest has already checked in").

The elegant part: BookingStatus.blocks_room is True only for CONFIRMED and CHECKED_IN, and availability (Lesson 27) asks nothing else. Cancelling frees the room instantly — no deletion, no special case, history kept.

3. Liraz: the game server

Every command handler starts with one question — "is this allowed in the current state?" — and every arrow is one method: start_game, next_question, close_question, end_game.

❓ A player's ANSWER arrives 10 ms after the timer closed the question. The timer already moved the state to SCORING → record_answer replies ERROR not_accepting. The server's clock is the authority; 10 ms late is late.

4. A guarded transition in code

    if booking.status is not BookingStatus.CONFIRMED:                    # is this arrow allowed from here?
        raise BookingError(f"Cannot check in: the booking is {booking.status.value}")
    if today < booking.stay.check_in:                                    # the guard
        raise BookingError("Cannot check in before the arrival date")
    booking.status = BookingStatus.CHECKED_IN                            # the transition
    ...

5. Why it makes the program correct and testable

  • Impossible situations become impossible: an answer can't be scored twice — scoring only happens on the QUESTION → SCORING transition, which happens once.
  • Tests are simple: put the engine in a state, send an event, check the new state and the reply. No sockets, no GUI.
  • The diagram in the book is the code: every box is an Enum value, every arrow a method.

6. Liraz: time-based scoring

points = round(1000 × (15 − t) / 15),  never below 100 for a correct answer;  wrong / none → 0
0 s → 1000      3 s → 800      7.5 s → 500      14.9 s → 7 → raised to 100

t is clamped to [0, 15] (a late answer that slips through must not give negative points) and measured with the server's time.monotonic(). Leaderboard: sort by score, highest first; ties broken by name so the order doesn't jump between broadcasts.

Lesson 31 — TCP is a stream: sockets, the protocol and message framing

For: Liraz (LanGame stages 1–2)  ·  Time: 45 – 60 min Before: Python bytes/str, JSON  ·  After this: Lesson 32 (threads), Lesson 30 (the game FSM)

🎯 By the end, the student can

  1. Explain client/server, IP address and port, and the TCP handshake with a sequence diagram.
  2. Explain why TCP glues and cuts messages, and show it happening on a real socket.
  3. Write the newline-framing receiver (buffer += chunk; while "\n" in buffer: …).
  4. Explain the protocol design (type + payload, one JSON per line) and "never trust the other side".

1. The architecture

The server listens on a port (5050) and is the authority: it holds the game state and the clock, and broadcasts every change. Clients only send requests (JOIN, ANSWER…) and display what the server says.

2. Connecting — the handshake

TCP first opens a connection (SYN, SYN-ACK, ACK), then guarantees that bytes arrive complete and in order, re-sending lost packets. UDP guarantees nothing — fine for video, wrong for "who answered first".

3. The most important idea: TCP is a stream of bytes

TCP doesn't send "messages" — it sends bytes, like water through a pipe. The receiver's recv() gets whatever has arrived: half a message, or two and a half glued together. TCP promises the bytes, not where the cuts are.

Framing = marking where each message ends. LanGame uses a delimiter: \n after every JSON message (JSON never contains a raw newline, so it can't appear inside one). The other common way is a length prefix.

class MessageBuffer:
    def feed(self, chunk: bytes) -> list:
        self._pending += chunk                          # 1. append
        if len(self._pending) > MAX_MESSAGE_BYTES:      # 2. never trust the other side
            raise ProtocolError("too_large", ...)
        *complete, self._pending = self._pending.split(b"\n")   # 3. the LAST piece is incomplete: keep it
        return [decode(line) for line in complete if line]      # 4. every complete line → a Message

4. The protocol

{"type": "ANSWER", "payload": {"question_id": 17, "choice": 2}}\n
  • type — one of a fixed list (MessageType); the receiver switches on it.
  • payload — a dict whose keys depend on the type.
  • JSON: readable in Wireshark and in logs; every language parses it; adding a field doesn't break old clients.
  • The QUESTION message never contains the correct answer — a curious player with Wireshark would see it.

Never trust the other side: a malicious or buggy client can send 10 MB without a newline (→ too_large), invalid JSON, an unknown type, choice: 7. Each becomes an ERROR reply — the server never crashes.

5. Misconceptions

Student says Truth
"One send() = one recv()" Only by luck on localhost. On a real network, never assume it.
"It works on my computer, so it's fine" Localhost rarely cuts messages; the classroom Wi-Fi will. Test with the demo.
"recv(4096) returns 4096 bytes" It returns up to 4096 — whatever has arrived. 0 bytes = the other side closed.
"Put the correct answer in QUESTION, the client won't show it" Anyone can read the bytes.

Lesson 32 — Threads, race conditions and locks

For: Liraz (LanGame — server and client) · Ryan (camera thread, Lesson 26) · Eran/Liraz (SQLite and threads) Time: 45 – 60 min  ·  Before: Lesson 31  ·  After this: Lesson 33 (the database)

🎯 By the end, the student can

  1. Explain why the server needs threads (blocking recv()), and name LanGame's threads.
  2. Show a race condition step by step and reproduce one live.
  3. Fix it with a Lock and with, and explain the critical section.
  4. Explain deadlock, why LanGame uses one lock, and why the lock must be held briefly.
  5. Explain why only Tkinter's main thread may touch widgets (the queue).

1. Why threads at all

conn.recv() blocks: it waits until bytes arrive. One loop serving 4 players would sit waiting on player 1 while player 2's answer piles up. So: one thread per client (ClientHandler), plus the accept loop, plus Timer threads that close a question after 15 s. They all share one game state — in memory, fast, and dangerous.

2. The race condition — step by step

score += 800 is three steps: read, add, write. If thread B reads between A's read and A's write, A's 800 is overwritten — lost. The result depends on timing → a race condition. Python's GIL does not protect you: it keeps one bytecode at a time, and += is several.

3. See it happen

cd lessons/32_threads_locks
python race_demo.py          # 4 threads × 10,000 points without a lock → thousands lost
python race_demo.py --lock   # 40,000 every time

When a switch between READ and WRITE is rare, the bug is rare — your tests pass, and it fails in front of the class. That's the worst kind of bug. The lock makes it 0, always.

4. The lock

with self._lock:                      # take it (wait if another thread has it)
    player.score += points            # critical section: one thread at a time
                                      # released here - even if an exception was raised
  • Critical section = the code between take and release.
  • Always with: forgetting to release = every other thread waits forever.

5. Deadlock — and LanGame's simple rule

Two locks taken in opposite orders → each thread holds one and waits for the other → frozen, with no error. LanGame uses one lock around the whole game state: no ordering to get wrong.

6. Hold it briefly

Sending to 10 sockets while holding the lock makes every handler wait. Do the update and copy what must be sent under the lock; release; then send.

7. Threads and Tkinter

Tkinter is single-threaded: only the main thread may touch widgets. The client's reader thread puts messages into a queue.Queue; the GUI polls it with root.after(50, poll). (Same idea as Ryan's camera thread, Lesson 26.)

SQLite and threads: a connection may be used only by the thread that created it → one connection per thread (or per operation); Database.get_connection() handles this (Lesson 33).

8. Misconceptions

Student says Truth
"Python has the GIL, so I don't need locks" The GIL protects bytecodes, not your three-step update.
"The tests passed, so there's no race" Races depend on timing — they hide from tests. Reason about them, and test with the demo.
"More locks = safer" More locks = deadlock risk. One lock, held briefly.
"The reader thread can update the label directly, it works" Until it doesn't — Tkinter is not thread-safe. Use the queue.

Lesson 33 — The database: constraints, transactions, indexes, parameters

For: Eran (HotelManager) · Liraz (LanGame) · and every project with SQLite (all seven)  ·  Time: 45 – 60 min Before: basic SQL (SELECT, INSERT, WHERE)  ·  After this: the database chapter of the book

  1. Explain primary keys, foreign keys and CHECK constraints, and why the database checks what Python already checks.
  2. Explain a transaction (all or nothing) and write one with with db.connection() as conn:.
  3. Explain what an index is, read EXPLAIN QUERY PLAN, and show the speed-up with a measurement.

1. Constraints — the database says no

Every line above is a real sqlite3.IntegrityError from this lesson's script. Defence in depth: the Python check (DateRange) protects the user; the database check protects the data from any future bug, another program, or a manual edit.

constraint prevents
PRIMARY KEY two rows with the same id
UNIQUE two rooms called "102", the same guest twice
CHECK (check_out > check_in) a stay that ends before it starts
CHECK (status IN (...)) a typo ("confimed") becoming a state
REFERENCES rooms(id) ON DELETE RESTRICT deleting a room that has bookings
ON DELETE CASCADE orphan answers / invoice lines when the parent is deleted

⚠️ SQLite ships with foreign keys OFF. Every connection must run PRAGMA foreign_keys = ON, or RESTRICT and CASCADE silently do nothing. A favourite examiner question. (Database.get_connection() does it.)

2. Transactions — all or nothing

Check-out = update the booking + insert an invoice + insert its lines. Saving a LanGame game = 1 game + 8 players + 80 answers. If the program dies halfway, half-written data is worse than nothing. A transaction groups the writes: commit() makes them all real at once; rollback() throws them all away.

@contextmanager
def connection(self):
    conn = self.get_connection()
    try:
        yield conn            # the body of `with` runs here
        conn.commit()         # no exception → everything is saved
    except Exception:
        conn.rollback()       # any exception → nothing is saved
        raise
    finally:
        conn.close()

3. Indexes — measured

"Is room 5 free between these dates?" on 20,000 bookings: about 0.9 ms reading every row (SCAN) vs about 0.03 ms with an index (SEARCH … USING INDEX) — some 35× faster, and the gap grows with the table (100,000 rows: ~4.5 ms vs ~0.12 ms). Your own computer gives other milliseconds; the shape is always the same.

An index is a sorted copy of some columns, kept as a tree — like the index at the back of a book. The cost: a little space, and slightly slower inserts. Put indexes on the columns your important WHERE uses: Eran's (room_id, check_in, check_out), Liraz's (category, difficulty). Put the EXPLAIN QUERY PLAN output in the book — it is proof.

4. Parameters, never string formatting

db.execute(f"SELECT * FROM guests WHERE name = '{text}'")       # WRONG - the text becomes SQL
db.execute("SELECT * FROM guests WHERE name = ?", (text,))      # RIGHT - the text is only a value

5. Dates as ISO text

'2026-03-02' sorts correctly as text (year, month, day), so check_in < ? works on strings and the index can use it. Never '2/3/2026'.

6. Misconceptions

Student says Truth
"Python already validates, the CHECKs are redundant" They guard against every other way data gets in. Cheap insurance.
"I'll commit after every insert, it's safer" Then a crash leaves half a game. Commit once per logical operation.
"Indexes on every column" Each index costs space and insert time. Index what you search by.
"Foreign keys work by default" Not in SQLite. PRAGMA foreign_keys = ON, every connection.
